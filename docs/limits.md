# Input limits

Every limit on what tripcurve will read, with the basis it was derived from (limits are derived, not picked). The constants live in `src/core/limits.ts`, each with this basis in a comment. Tests take limits as parameters, so a test can use small values.

Dates are 2026. A value is "read" on the date given.

The design documents (requirements, user stories, the report mockups, the interaction spec and the build plan) were written before the code and are kept outside this repository; where this file cites one, the rule it set is restated here.

| Limit                | Value                                                  | Basis                                                                                                                                                                                                                                                                                                                                                                |
| -------------------- | ------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Per-file size        | 5 MB = 5,000,000 bytes (decimal)                       | The maintainer-confirmed performance envelope "files under 5 MB" and the wireframe wording "5 MB". A file over it is reported unchecked with the fixed reason `over-size` and the run continues.                                                                                                                                                      |
| YAML alias expansion | 100 (the `yaml` library's own default `maxAliasCount`) | `yaml` 2.9.1, read 2026-11-11: `Document.toJS` uses 100 when no value is given, and `options.d.ts` documents it as "Default: 100". The value is passed explicitly to every parse, so a change of the library default cannot silently remove the limit. `-1` disables the check and is never used. A file that exceeds it is unchecked with the reason `alias-limit`. |
| Nesting depth        | no number                                              | No number is picked. A parse or a walk that overflows the stack throws `RangeError`; the file boundary catches it and reports the file unchecked with the fixed reason `too deeply nested`. A hostile fixture proves the tool does not crash.                                                                                                                        |

## What intake does at each limit

Intake (`src/parse/intake/`) applies these limits and records each refusal as an unchecked input with a fixed reason code and no parser message. The run goes on.

| Case                                          | Reason code    | Notes                                                                                                                                                                                                                  |
| --------------------------------------------- | -------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| File or stream larger than 5,000,000 bytes    | `over-size`    | The size is read from the open file handle before any byte is read. A file of exactly 5,000,000 bytes is read. A YAML file that is over the limit cannot be classified by content, so it is reported rather than ignored. |
| YAML alias expansion over 100                 | `alias-limit`  | `toJS` is called with `maxAliasCount: 100` on every document.                                                                                                                                                          |
| Stack overflow while composing or converting  | `over-depth`   | See "Nesting" below.                                                                                                                                                                                                   |
| Not valid UTF-8, or a NUL byte                | `unreadable`   | Never decoded with replacement characters. A UTF-8 sequence cut off at the very end of the file is `truncated`.                                                                                                        |
| A file that changed size while it was read    | `truncated`    | What was read is not the whole file, so it is not used.                                                                                                                                                                |
| YAML syntax error, duplicate key              | `parse-error`  | With the line of the first error. One record per file, however many documents fail; the documents that parsed are still read.                                                                                          |
| A Kubernetes object whose name or namespace is not literal text (for example an unquoted Helm `{{ }}` name), whose `apiVersion` is present and not text, or a root list of objects with no text `kind` | `object-not-identified` | Added after intake by the analysis, one record per file, so the object is never dropped without trace and the run is Incomplete. Fixed wording: "a Kubernetes object could not be identified". A file already unchecked for another reason keeps that reason. |
| A CloudFormation or SAM template with a transform or macro other than `AWS::Serverless-2016-10-31`, or `Fn::Transform` anywhere (with or without `Resources`) | `cfn-transform` | Added after intake by the template reader (B12). Fixed wording: "uses a CloudFormation transform or macro that can rewrite the template". The values of its resources are UNRESOLVED. |
| A template tripcurve does not read: an alias, a merge key, a collection key or a tagged key, several documents, a `Resources` that is not a mapping, an `AWS::Serverless` resource without the SAM transform, a resource with no readable `Type` | `cfn-unreadable` | Fixed wording: "CloudFormation or SAM syntax that tripcurve does not read" (B12). |
| A file that is a Kubernetes object and a template at once, or (for the file named as the root) a Terraform plan and a template | `template-ambiguous` | Read as neither (B12). |
| A syntax error, or a key written twice, in a `.json` file | `json-parse-error` | Like `parse-error`, worded for JSON: "JSON syntax error (or a key written twice)" (B12). |
| A Node or TypeScript source that does not parse | `source-parse-error` | With the line of the first error; worded "syntax error in a source file" (B21). Nothing is read from the file, and what depended on it is UNRESOLVED. |
| A Node or TypeScript source with more than 500,000 syntax nodes | `source-too-large` | Worded "source too large to read safely" (B21); nothing is read from the file, and what depended on it is UNRESOLVED. |
| Link or `..` that leaves the root             | `outside-root` | See "Symlinks" below.                                                                                                                                                                                                  |
| Symlink cycle, or a link chain that never ends | `symlink-loop` |                                                                                                                                                                                                        |
| Anything the operating system refuses         | `unreadable`   | Permission denied, a file that vanished, a socket, a pipe or a device (never opened, so it cannot block).                                                                                                              |

`over-count` is in the contract's list of reason codes and is never produced: there is no count limit.

### Duplicate keys

The `yaml` library's own duplicate-key check compares each key with every key before it, so it is quadratic in the number of keys in one map: 30,000 keys took 6.9 s and 60,000 took 25.7 s (measured 2026-11-11, Node 22.23.2, macOS arm64), well under the 5 MB cap. Intake therefore parses with `uniqueKeys: false` and finds a repeated key itself, in one pass with a set per map, over the text of scalar keys (the same rule as the library: a number and a string are different keys). The result is unchanged: a repeated key is a `parse-error` at the line of its second occurrence. The library's own warnings are switched off (`logLevel: 'silent'`), so nothing the input contains reaches standard error.

### Nesting

No nesting number is picked. The `yaml` library composes nodes recursively and catches a stack overflow itself, reporting it as the error code `RESOURCE_EXHAUSTION` (read in `compose-node.js` of the installed yaml 2.9.1, 2026-11-11); intake maps that code, and any `RangeError` from its own walk, to `over-depth`. The depth at which this happens depends on the stack of the machine and the Node build, so a file near the edge may be read on one machine and refused on another. Measured on 2026-11-11 with Node 22.23.2 on macOS arm64: block-style nesting of 600 levels parsed and 1000 levels was refused; flow-style nesting of 500 levels parsed and 700 was refused. Real Kubernetes manifests nest about a dozen levels.

### Symlinks and spellings

One rule: a directory is never entered through a symlink; a real directory is walked where it really is.

- A symlink to a directory outside the root is not read (`outside-root`).
- A symlink to the directory it sits in, or to one of that directory's ancestors, is `symlink-loop`.
- A symlink to any other directory inside the root is ignored: the real directory is walked in its own place.
- A symlink to a file inside the root makes that file a candidate under its real name.
- A symlink to a file outside the root is not read; it is reported (`outside-root`) when the link's name or the target's name is one tripcurve reads.

Two spellings of one file are one file: files are identified by device and inode, so a hard link, a symlink, a trailing slash, a symlinked parent, a Unicode form or a case difference (where the file system treats them as equal) each give one read and one count. The canonical path is the real path, relative to the root.

Directories named `.git` and `node_modules` are never entered.

## Documented value ranges

These are not input limits: they are ranges the cloud provider documents for a setting. A value outside the range is not used as the setting's value.

| Setting | Range | Basis |
| --- | --- | --- |
| ALB `idle_timeout.timeout_seconds` | 1 to 4000 seconds | https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html, read 2026-11-11: "The valid range is 1 to 4000 seconds." |

A value outside the range, read from the `load-balancer-attributes` annotation or declared as `load_balancer.idle_timeout_s` in `tripcurve.yaml`, gives an unresolved LB idle with the fixed reason "outside the documented range 1 to 4000 s". The constants are in `src/core/limits.ts`.

## Where there is no separate limit

There is no limit, and so no number to defend, for:

- documents per file;
- line length;
- total files;
- total bytes.

There is no basis for a number for any of these. The per-file limit, root confinement and symlink-loop detection already bound the work, and tripcurve uses no wall-clock timer.

## Text shown in a report

One output line is at most 80 columns (interaction spec, rule 5). Quoted input text is cut with `...` to fit the room it has, and the default cut is the 80-column line width (`TERMINAL_WIDTH` in `src/core/safe-text.ts`). JSON and SARIF text is not cut by default.

## Node readers

- **Import depth.** No number is picked. The source reader follows relative imports from the linked entry file, each file once, so the work is bounded by the files intake already read (and by the per-file limit). `readNodeServer` takes an optional `maxImportDepth` for tests. A relative import that names no file in the input makes the search incomplete, so an absent setting is not taken as "the default applies".
- **Nesting.** A source file or `package.json` that overflows the stack while parsing or walking is caught at the file boundary and reported unchecked as `over-depth`; a syntax error in a source file is `source-parse-error` (B21; it was `parse-error`, worded for YAML). Neither reads anything from the file.
- **Read forms (B1).** Assignments `x.name = v` and `x['name'] = v`, the options object of `createServer(...)` (an object literal, or an identifier that is a single `const` object literal in the same file) and an object literal given to `Object.assign`. A value is a numeric literal (digit separators, hex, exponent), a unary minus, or a product of literals. Other forms (for example `new http.Server(...)`, a framework's own server options) are not read, so a program that sets a timeout only that way shows "no setting found" if it also has a `createServer` or `.listen` call; this is a known gap until a later bolt.
- **createServer arguments (allow-list).** "No setting found" stands for the Node default only if every http or https `createServer` call is in an allowed form: no argument; a handler (a function or arrow written in place, an identifier bound to exactly one `const` arrow or `function` declaration, or something traced to `express()`, including an Express app exported by a local file); an options object written in place with literal keys and no spread; or a `const` options object referenced nowhere else in the file except this one argument and plain property reads; or an options object followed by a handler. Anything else (a call result, a spread, a member access, a conditional, `??`, an identifier from elsewhere, an imported value that is not an Express app) makes the search incomplete with the reason "the createServer arguments are not in a form tripcurve reads". No handler is assumed for a single unknown argument. Reason: any other form can hold a timeout setting, and following every way a value can reach `createServer` cannot be closed one form at a time.
- **Image tags (B1, widened in B3).** `X.Y.Z` is exact, `X.Y` is `X.Y.x` and `X` is `X.x`; version parts have no leading zeros and at most 15 digits (`22.023.2` is unknown). `lts`, `current`, `latest` and a missing tag (which means latest) are all versions. A tag may carry at most ONE suffix, taken from a written-out list of official variants: `-alpine`, `-alpine<N>.<N>` (for example `-alpine3.20`), `-slim`, `-bookworm`, `-bookworm-slim`, `-bullseye`, `-bullseye-slim`, `-trixie` and `-trixie-slim`; it does not change the version. Any other suffix, two suffixes (`-alpine-slim`), a leading `v`, a fourth number and an empty tag are unknown with a fixed reason: tripcurve does not guess what an unfamiliar word means. A tag written with a digest is unknown (the runtime pulls the digest, so the tag is only a label). See "Node version ranges and the explicit idle close (B3)" below.

## Known limits (second review pass)

- **IngressClassParams `spec.group.name`.** An IngressGroup set through the class parameters (an `IngressClassParams` object that an `IngressClass` points to) is not visible to the reader. Only the `group.name` annotation and a repeated `load-balancer-name` mark a shared ALB. Reason: tripcurve reads `IngressClass` only for its controller string, and a group named there would need the parameters object to be read and linked.
- **A Node version that does not exist (m2).** A tag such as `node:22.99.9` falls inside a knowledge-base range and resolves. tripcurve reads no release list: that needs the network, which `check` never uses. The range is anchored by the lowest measured version of its release line, not by a list of published releases.
- **Declared `runtime.node` outranks the image tag (m4).** By the design, a declaration wins, and no note is printed when it differs from the image tag. Reason: the declaration is the user's statement; a note would be a new output line outside the approved grammar.
- **Environment files.** tripcurve reads no `.env` file, so every `--env-file` and `--env-file-if-exists` is a gap ("environment file not read"), even when the file is local and has no `NODE_OPTIONS` line. Reason: Node applies `NODE_OPTIONS` from such a file (https://nodejs.org/docs/latest-v22.x/api/cli.html, read 2026-11-11), and intake does not classify `.env` files.
- **Computed member writes.** `server[k] = v` with a computed key is a gap when the receiver traces to a server or is the options object of `createServer` (or an alias of it). Any other receiver that cannot be traced is not flagged, because that would flag every array and map write in a program.

## What Node loads from `NODE_OPTIONS` (measured 2026-11-11)

Run with `NODE_OPTIONS="<variant>" node -e 0` in a temp directory holding a tiny `p.js` (prints `LOADED`), `p.mjs` and a loader `l.mjs`, on Node 22.23.2 (`/opt/homebrew/opt/node@22`) and the official 22.23.5, 24.22.3 and 26.13.1 builds. The result was identical on all four versions.

| Variant | Loads the file? |
|---|---|
| `-r ./p.js`, `--require ./p.js`, `--require=./p.js` | yes |
| `--import ./p.mjs`, `--import=./p.mjs` | yes |
| `--loader=./l.mjs`, `--experimental-loader=./l.mjs`, `--experimental_loader=./l.mjs` | yes (loader runs; an ExperimentalWarning is printed) |
| `"--require" ./p.js`, `--require "./p.js"` (double quotes) | yes |
| `--max_old_space_size=100 --require ./p.js` (underscores in another option) | yes |
| `'--require' ./p.js` (single quotes) | no, accepted silently |
| `-r=./p.js`, `-R ./p.js`, `--REQUIRE ./p.js`, `--rEquire ./p.js`, `--require\ ./p.js` | no, Node refuses to start ("is not allowed in NODE_OPTIONS") |
| `require=./p.js`, `require ./p.js`, `r ./p.js`, `import=./p.mjs` (no dashes) | no, accepted silently |
| `--require_module`, `--im_port`, `--import_x` | no (other or unknown options; refused on 22.x, accepted on 24 and 26 for `--require_module`) |
| `--env-file=.env`, `--env_file=.env`, `--env-file-if-exists=.env`, `-e 1`, `-p 1`, `--eval 1` | no, refused: "is not allowed in NODE_OPTIONS" |
| `--report-on-signal` | no, not code-loading |

The guard is a superset: a name is matched after stripping leading dashes, turning `_` into `-` and lower-casing, against exactly `r`, `require`, `import`, `loader`, `experimental-loader`, `env-file` and `env-file-if-exists` (and the eval options); a value holding a quote or a backslash is a gap. `--report-on-signal`, `--report-dir`, `--redirect-warnings` and similar options do not load code, so they are not gaps. The unquoted no-dash forms did not load on these versions but stay gaps (superset; the docs say prefixes are stripped).

## Python server readers

Everything here is read from files and never run. A setting is a list of contributions, one per place that sets it (the command line, `GUNICORN_CMD_ARGS`, a linked Dockerfile's `ENV`, the config file). A place that could set a setting and was not read is an UNRESOLVED contribution to every setting it could touch, so "no source sets it" (and with it the default `sync` worker or a knowledge-base default) means every place was read.

- **Where gunicorn takes settings from.** The command and its args; `GUNICORN_CMD_ARGS` from a literal manifest `env` value only (a `valueFrom`, an `envFrom` or the variable twice makes it unread); a Dockerfile `ENV` only when `tripcurve.yaml` links that Dockerfile to the workload; the file `-c`/`--config` names or a `gunicorn_config:` link; a `gunicorn.conf.py` in the working directory when neither is given (an unlinked one anywhere in the checked files makes every setting UNRESOLVED: "may be loaded from the working directory; link it in tripcurve.yaml"). A manifest `env` value replaces the image's `ENV` of the same name, and replaces an `envFrom`.
- **Not seen.** An image's own `ENV GUNICORN_CMD_ARGS` when the Dockerfile is not linked, and a config file baked into an image, are not visible (the requirements said so). The default (sync worker, or a knowledge-base default) is therefore "nothing in the files sets it", not "the running server has none".
- **Flags read.** gunicorn: `-k`/`--worker-class`, `--threads`, `--keep-alive`, `--graceful-timeout`, `-w`/`--workers`, `-c`/`--config`, and `--chdir` (only to know it was given). uvicorn: `--timeout-keep-alive` and `UVICORN_TIMEOUT_KEEP_ALIVE`. Forms read: `--flag value`, `--flag=value`, `-kvalue`, `-k value`.
- **Forms that are NOT read and are UNRESOLVED for the setting they could be:** an abbreviation of a long flag (argparse accepts unambiguous prefixes, so `--keep` is a prefix of `--keep-alive`), `-k=x`, a clustered short flag such as `-Dk`, a flag with no value, a value that is not a whole number of 0 or more, a worker class that is not exactly one of `sync`, `gthread`, `gevent`, `eventlet`, `tornado`, `uvicorn.workers.UvicornWorker`, `uvicorn_worker.UvicornWorker`, and any word with a `$(...)` reference that could expand into a flag (`$(FLAGS)`, `--$(X)`): that makes every setting of that origin unresolved. A `$(...)` inside a flag value makes only that setting unresolved. Reason: Kubernetes expands `$(NAME)` from environment variables the files may not show.
- **`GUNICORN_CMD_ARGS` is split as Python's `shlex.split`** (quotes, single quotes, backslash escapes); a value shlex cannot split, one with a `$(`, or one that names `-c`/`--config` leaves every setting unresolved.
- **The program.** `gunicorn`, `uvicorn`, `python -m gunicorn`, `python -m uvicorn` (any `python`, `python3`, `python3.12`). `poetry run gunicorn`, `sh -c "gunicorn ..."` and `python -u -m gunicorn` are not read, so the server is not identified.
- **`gunicorn.conf.py` is not Python to tripcurve.** Only top-level lines `name = <literal>` are read (an integer, a float, a one-line quoted string with no escapes, `True`, `False`, `None`), plus blank lines, comments and a one-line string. The first statement of any other kind (an import, a call, an `if`, a `def` or `class`, a computed value, an augmented, tuple, chained or annotated assignment, `exec`, a star import, a continuation line, two statements on a line, an indented line) makes every setting of the file UNRESOLVED, with that line number, even a setting assigned a literal earlier. Reason: code that is not read could set or reset any setting, and a `def` hook can change `cfg` at run time. A setting assigned a value that is not a literal names its own line. Only the exact lower-case names are looked at, as gunicorn does.
- **Config file names.** Only a file named exactly `gunicorn.conf.py` is read as a gunicorn config (intake's classification). `-c settings.py` or a link to another name is UNRESOLVED ("the config file is not named gunicorn.conf.py, so it was not read as a gunicorn config"). Reason: intake reads no other `.py` file, and reading every Python file is more input than this release takes.
- **Dockerfile `ENV`.** The last build stage and the earlier stages of the same file it is built `FROM`; a later `ENV` overrides an earlier one; a base image that is not a stage of the file may carry `ENV` that is not seen. A value with `$`, a backslash or a backtick is not read, and a `# escape=` directive makes every name unread.

### Worker model and setting precedence

- **Order.** The worker class is resolved before any keep-alive default. The default class is `sync`, which closes after every response: T1 is N/A, the source is the flag, config line or env value that named it, or, for the default, the command (`no -k given`). `--threads` above 1 with the sync worker means gthread (measured on 26.2.0 and 27.0.0: gunicorn logged `Using worker: gthread`, `measure/results/2026-11-11-b2.jsonl`). `--threads 0` and `1` stay sync.
- **Measured precedence, for `keepalive` only.** Command line, then `GUNICORN_CMD_ARGS`, then the config file (`-c`'s file, or `./gunicorn.conf.py` only when no `-c` is given; `-c` stops the default file from being loaded). Source: `measure/results/2026-11-11-b2.jsonl` and the table in `measure/README.md`: every single source, all 6 pairs, all 4 triples and the quadruple, on gunicorn 26.2.0 and 27.0.0, darwin-arm64. The one function that holds it is `resolveSettingPrecedence` in `src/resolve/gunicorn-precedence.ts`.
- **Inference, not a measurement.** The `keepalive` precedence was measured with the uvicorn worker only. It is applied to every worker class on the inference that precedence is settled in gunicorn's configuration layer before any worker exists, so it does not depend on the worker class. That has not been measured on gthread or any other worker.
- **Not measured, so UNRESOLVED when sources disagree:** every other setting (`--threads`, `-k`/worker class, `--graceful-timeout`, `-w`), with the reason "gunicorn setting precedence not yet measured for this setting"; the same flag twice with different values; `-c` inside `GUNICORN_CMD_ARGS`; two `-c` sources (two `-c` flags, or a `-c` and a link that name different files); `--chdir` (the config file is then not read); a `python:` config. For `keepalive`, a source that could not be read ranks only against sources at its own level or above: an unread lower source cannot change a higher one, an unread higher source leaves the setting unread.
- **An unlinked repository `gunicorn.conf.py`** still leaves the worker class unresolved even when the command names it, because the class precedence is not measured. It does not leave `keepalive` unresolved when the command sets `keepalive`.
- **An explicit `keepalive` equals the idle close, only where measured.** Entries of subject `gunicorn-keepalive-explicit` (and `uvicorn-keepalive-explicit`) in `src/kb/data/python-servers.json` say for which worker class and releases the idle close was measured equal to the explicit value; they hold no number and cite the lines. Covered now: uvicorn alone on 0.54.x from 0.54.0 (explicit 7 s from `--timeout-keep-alive` and from `UVICORN_TIMEOUT_KEEP_ALIVE`, explicit lines 16 to 27), the uvicorn worker on 26.x from 26.2.0 and 27.x from 27.0.0 (explicit 3, 5, 7 and 9 s from each of the command line, `GUNICORN_CMD_ARGS`, a `-c` file and `./gunicorn.conf.py`, `measure/results/2026-11-11-b2.jsonl`; 75 s on 26.2.0 from `docs/research.md` section 2), and gthread on 26.x from 26.2.0 and 27.x from 27.0.0 (explicit 7 s and 75 s, `measure/results/2026-11-11-b2-explicit.jsonl`); the uvicorn worker on 27.0.0 at 75 s is in explicit lines 13 to 15. In every measured run the idle close was at or above the setting, never below, so a result that needs `idle close > LB idle` is sound; the deviation above nominal grows with the value on gthread (up to 137 ms at 75 s), which the entry's `toleranceMs` records. Inference: any whole number of 1 or more follows the same rule; only 3, 5, 7, 9 and 75 were measured, and 0 is not covered. Everything else stays UNRESOLVED ("the effect of an explicit keepalive on the idle close is not measured yet", with the value and line shown): gevent, eventlet and tornado, gthread or the uvicorn worker on a release outside the covered lines, and uvicorn alone on a release outside 0.54.x. The idle close is printed with a short basis such as `measured: explicit value applies (3 to 75 s on 26.2.0)`, and the setting's own file and line stay in the chain as the `keepalive` step. The nominal value is compared (strictly greater than the load balancer idle; equal is FAIL): the overshoot is never below nominal, so using it can only make a verdict stricter. A value found in the command, `GUNICORN_CMD_ARGS` or the config file is used through the precedence function, so the measured winner is the one used.
### The gunicorn and uvicorn version (maintainer decision 2026-11-11)

- **Order.** A `runtime.gunicorn` or `runtime.uvicorn` declaration for the workload (a string, same rules as `runtime.node`; a bare number is refused; a declaration naming no workload or two is the config-error case error); else an EXACT pin in the repository; else UNRESOLVED ("no gunicorn version in the files", declare `runtime.gunicorn` in tripcurve.yaml). A declaration wins over pins that disagree with it. A declared `26` is the whole of 26.x, so a knowledge-base entry that starts at 26.2.0 does not cover it: UNRESOLVED.
- **Pin files** (class `python-pin`, read by a hand-written line reader in `src/parse/python/read-pins.ts`, no TOML dependency): `requirements*.txt` (`name==X.Y.Z`; extras, `--hash` options and comments ignored); `pyproject.toml` (PEP 621 `dependencies` of `[project]` with `==`, and the exact forms of `[tool.poetry.dependencies]`: `"26.2.0"`, `"==26.2.0"`, `{version = "26.2.0"}`); `poetry.lock` and `uv.lock` (the `version` of the `[[package]]` block of that name). `>=`, `~=`, `^`, `~`, `*`, a range, a comma list and an unpinned name are not pins. Optional dependencies, dependency groups and dev groups are not read.
- **Environment marker.** An exact pin under an environment marker (`gunicorn==26.2.0; python_version<'3'`) applies only where the marker holds, so it is not read: UNRESOLVED ("the gunicorn pin applies only under an environment marker"). A marker on another package or on a line that is not an exact pin changes nothing.
- **Option lines and URL requirements.** In a `requirements*.txt`, a line that starts with `-r`, `--requirement`, `-c`, `--constraint`, `-e` or `--editable` (glued or spaced) and a requirement that is a URL, a path, a wheel or archive file name or any text that is not a requirement make that file unreadable for the package, whatever package they name: they can install or constrain the package at another version. Other options (`--index-url`, `--extra-index-url`, `--pre`, `--no-binary`, `--hash`) bring in no requirement and are ignored. A Poetry sub-table `[tool.poetry.dependencies.gunicorn]` is a form that is not read.
- **Not read, so UNRESOLVED ("a gunicorn pin in the repository is not in a form tripcurve reads"):** a pre-release, a local version, a version of four parts, `===`, a direct URL, a VCS line naming the package in its `egg=` fragment, a Poetry git or path dependency, an unterminated or multi-line-string `dependencies` array, a lock block with no plain version. A pin that cannot be read is never skipped for another file.
- **Which files.** The nearest folder, from the manifest's folder up to the root (the B1 working-directory search), that has a pin file mentioning the package in ANY form (an exact pin, `>=`, a range, no version, a marker), a pin file that cannot be read, or a pin file that intake skipped. That folder is the answer: an exact pin there is used; a file that names the package without one gives UNRESOLVED ("gunicorn is not pinned to an exact version in the files"), a skipped one gives "a gunicorn pin file was skipped: larger than the 5 MB limit"; the search never goes on to a parent folder's pin. Pin files in a folder that is not on that path are not candidates. ### Review fixes (B2 adversarial review)

- **PEP 263 coding cookie.** A `coding[:=]name` on line 1 or 2 of a `gunicorn.conf.py` is read. Only `utf-8`, `utf8`, `ascii`, `latin-1`, `latin1`, `iso-8859-1` and `iso8859-1` (case-insensitive, `_` as `-`) are plain; any other encoding, and any file showing NUL characters or a UTF-16 mark, makes every setting UNRESOLVED ("gunicorn.conf.py declares a source encoding that tripcurve does not read"). The rule applies to a file named by `-c`, a link, and the default file alike.
- **Explicit keepalive span.** An explicit-setting entry records `measuredSpan` (the smallest and largest explicit value measured); the rule applies only inside it, otherwise "explicit keepalive N s is outside the measured span (A to B s)". A skipped pin file in the nearest folder is UNRESOLVED with its reason.

## The shutdown chain: T2, T3 and in-process drains (B4, 2026-11-12)

What the rules read, what each knowledge-base entry claims, and what is not covered. The data is `src/kb/data/shutdown.json`; each entry's `notes` cite the result lines in `measure/results/2026-11-11-b4.jsonl`, and `test/kb/shutdown-evidence.test.ts` checks every claimed release, worker class, value and source against those lines and `measure/results/2026-11-11-lookups-b4.txt`.

### What was measured and what the entries claim

- **Kubernetes default grace period: 30 s, `documented`.** The pod lifecycle page, read 2026-11-12: "The default terminationGracePeriodSeconds setting is 30 seconds." Not measurable without a cluster (no cluster is used), so the entry carries a reason instead of a script. It is used only when the pod spec sets no `terminationGracePeriodSeconds`: the file itself then shows that the API server applies the default, so it may support a PASS. A value in the file that is not a whole number of 0 or more (`"45"`, `-5`, `4.5`) is UNRESOLVED and never falls back to the default.
- **gunicorn `graceful_timeout`: 30 s, measured on 26.2.0 and 27.0.0** for the sync worker, gthread (`--threads 2`) and the uvicorn worker (uvicorn-worker 0.4.0 with uvicorn 0.54.0): a request still running at SIGTERM was cut after 30003 to 30099 ms, three runs each. `--timeout 120` did not move it. The printed basis is `measured on 26.2.0` (or `27.0.0`), per major line, from the measured release to the end of that line (the B2 convention); other releases, other major lines, and the gevent, eventlet and tornado workers have no entry and are UNRESOLVED.
- **An explicit `--graceful-timeout 10`: measured in these forms only** (`measure/results/2026-11-11-b4.jsonl` and `-b4-more.jsonl`, gunicorn 26.2.0 and 27.0.0, three runs each, any worker count that was run: `-w 1` and `-w 2`). The command-line flag for the sync worker, gthread and the uvicorn worker; `GUNICORN_CMD_ARGS='--graceful-timeout 10'` and a `-c` file with `graceful_timeout = 10` for the sync worker only (a value in a linked Dockerfile `ENV` of `GUNICORN_CMD_ARGS` is the same variable at run time and counts as the environment form). The printed basis is `measured at 10 s on 26.2.0`. Any other value, another worker class in these sources, or another place is UNRESOLVED ("an explicit graceful timeout from GUNICORN_CMD_ARGS was not measured for the gthread worker"). Two sources that set it are UNRESOLVED unless they agree: precedence was measured for `keepalive` only. The default 30 s was also run with `-w 2`, so it does not depend on the worker count.
- **uvicorn alone has no ceiling by default.** A 60 s request in flight at SIGTERM finished in full (59452 to 59456 ms later; the cap on the wait was 90 s), so without `--timeout-graceful-shutdown` the ceiling is unknown and T3 is UNRESOLVED with "declare longest_request_s". `--timeout-graceful-shutdown 5` on the command line (the `=` form is the same flag) cuts the request after 5116 to 5152 ms: the entry is measured at 5 s on uvicorn 0.54.0 only. The environment form `UVICORN_TIMEOUT_GRACEFUL_SHUTDOWN` was not measured and is never used; its mere presence (or an `envFrom`, an env file) makes the setting unresolved.
- **lightship `shutdownDelay`: 5000 ms under Kubernetes, measured on 9.1.0** with `KUBERNETES_SERVICE_HOST` set (the handlers started 5002 to 5004 ms after SIGTERM; with the variable unset the delay is 0, as the README documents). - **terminus `beforeShutdown` has no default delay** (README of 4.12.1, read 2026-11-12: the 5000 ms is only in the README example), so only a delay written in the code counts. Whether terminus's `timeout` (default 1000 ms, "number of milliseconds before forceful exiting") also limits `beforeShutdown` is not in the README and was not measured. ### Where the lightship release comes from

An exact pin in `package.json` (`dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`), or the locked version in `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock` (classic and berry) or `pnpm-lock.yaml`, in the nearest folder from the entry file's folder up to the root that names the package at all (the rules of the Python pins). A range alone (`^9.1.0`) is not a pin; a range in `package.json` with an exact version in the lock file in the same folder is the lock file's version. An alias, a git, file, link or workspace spec, a pre-release, an `overrides`, `resolutions` or `pnpm` entry that names the package, a lock file that does not parse, a nested copy with a different version, or a file skipped for size is UNRESOLVED ("declare drain.in_process_s") and never lets the search go on to a parent folder. The file is named in an Assumption. Cost: a repository with a lock file over 5 MB is reported "not checked" (intake's limit), as `poetry.lock` is.

### Drains in Node source (the allow-list)

A drain counts only when the call or registration is a plain statement that runs from the top of the file (the file itself, or a function it calls by name), is tied to the process (lightship, a handler on the global `process`) or to the ONE listening server of the file (terminus, the `close` of a handler), and is written in one of the forms below with a number written in the code. Anything else that looks like a drain is a drain of UNRESOLVED duration, with "declare drain.in_process_s"; it is never "no drain" and never a guessed delay.

- **lightship:** `createLightship()` or `createLightship({...})` whose keys are among `shutdownDelay`, `port`, `gracefulShutdownTimeout` and `shutdownHandlerTimeout`. `detectKubernetes`, `signals`, `terminate`, a spread, a non-literal `shutdownDelay`, a call under a condition or in a callback, an alias of `createLightship`, and passing it to another function are unresolved.
- **terminus:** `createTerminus(server, { ... })` with an options object written in place, keys from terminus's documented list, `signal` only as `'SIGTERM'`, `server` the listening server (a variable assigned once, or the result of its own `.listen(...)`). `beforeShutdown` is a function in place or a local function, and its body is log calls and delays only: `new Promise(r => setTimeout(r, N))`, also written `function (resolve) { setTimeout(resolve, N); }`, or `await sleep(N)` with `sleep` from `timers/promises`; N a number or a product of numbers. A helper that sleeps, a condition, a loop, a call before the delay, `signals`, and an options object that is not in place are unresolved. An Express app served through `app.listen(...)` is a server the settings reader cannot name either (B3), so a terminus on it is unresolved; `http.createServer(app)` works.
- **SIGTERM handler:** `process.on`, `.once`, `.addListener`, `.prependListener` or `.prependOnceListener` with the literal `'SIGTERM'` and a handler written in place or a local function. The handler is a list of statements: log calls, delays, then the statement that stops the server (`<server>.close(...)` on the listening server, or `process.exit(...)`), after which anything may follow (a kill timer after the stop is not a drain); or a single `setTimeout(() => <stop>, N)` followed only by log calls. A kill timer before the stop, a second stop beside a timed stop, a condition, a helper, or a handler that never stops the server is unresolved. A handler that stops the server at once is a drain of 0 s (no drain). Other signals are not drains.
- **`process` used in any other way** (`const p = process`, `process[x]`, `globalThis.process`, `const { on } = process`, `require('process')` used inline, `process` passed to a function) makes the search for a handler unresolved; reading `process.env`, `process.argv`, `process.exit` and a few other members is ordinary. A name bound by `import x from 'node:process'` counts as the process. More than 200 registrations in one file are one unresolved drain.
- **Two or more drains** in the files read (lightship and a handler, two handlers, ...) are UNRESOLVED ("how they combine is not read"): independent handlers run side by side, so the server may stop at the earliest.
- **More than one server listening** in the files read: a terminus or handler cannot be tied to the one that serves, so it is unresolved.
- **Not read, so not found:** a drain made by another package (`close-with-grace`, `http-terminator`, a framework's shutdown hooks), by code that is not in the files read, or by an environment variable. "No drain found" for a Node workload means exactly "no lightship, terminus or SIGTERM drain in the N files read, and the source search was complete" (the detail line says so); T2 is FAIL only then. A package that registers its own signal handler without being handed the server can delay the server and is not seen. A Node search that is not complete (the B1 gaps) with no drain found is UNRESOLVED, never FAIL.

### Rules T2 and T3

- **T2.** PASS: a preStop delay above 0 (`exec sleep N`, `exec /bin/sh -c sleep N`, the `sleep` handler), an in-process drain above 0 s that was read, or a declared `drain.in_process_s` above 0. A delay of 0 is not a drain. FAIL: none of these, and the search was complete (Node source linked and read in full, or gunicorn or uvicorn, where the detail line says "in-process drains are read for Node source only; none declared"). UNRESOLVED: a Node workload with no preStop whose source is not linked; a server that is not recognised; a Node search that is not complete; a preStop hook of unresolved duration; an in-process drain of unresolved duration, **even when a preStop delay or another drain exists** (maintainer decision 2026-11-10: nothing shows PASS over an unverified value).
- **A declared drain settles what the files cannot show.** `drain.in_process_s` replaces an in-process drain whose duration is unknown or not read (the recovery table of the interaction spec). It cannot lower a drain the code shows: when both are known, the larger counts and the chain shows both. A declared drain of 0 with no drain found is FAIL (the maintainer said there is none).
- **Two `workloads:` entries that name one workload are a configuration error** (the config-error case, "two entries name the same workload"), checked by name with namespaces and kinds that do not exclude each other. Nothing is merged, so no declaration is chosen over another by its position. A declaration for an unknown workload prints that workload's name and its line.
- **A preStop hook is not settled by a declaration.** The interaction spec's recovery table lists `drain.in_process_s` for "terminus or hook of unknown duration", but the requirements make a hook UNRESOLVED and there is no key that declares a hook's duration, so a hook stays UNRESOLVED for T2 and T3 whatever is declared; the line says to write the preStop as `sleep N` so its delay can be read. This is a reading chosen between two design documents that disagree.
- **T3.** `grace >= preStop + drain + L + 1 s`, in whole milliseconds so no float error can move a verdict. L is the declared `longest_request_s` (per workload), else the server's ceiling. NOT EVALUATED when T2 is FAIL. UNRESOLVED when the grace period, the preStop, the drain or L is not established: a hook, an unknown drain, an unlinked or incomplete Node search with no declared drain (the drain term cannot be assumed 0 for a Node source that was not read in full), no ceiling and no declaration (every Node server, uvicorn alone, gunicorn outside what was measured). With a ceiling and no declaration: PASS or WARN ("workers are killed only if a request is still running (grace - preStop - drain) s after SIGTERM"; when preStop and drain already use the whole grace period the line says the grace period ends before the server can stop). With L declared: PASS or FAIL. A value above what whole milliseconds can hold is UNRESOLVED.
- **For gunicorn and uvicorn the drain term is 0 s unless declared.** In-process drains are read for Node source only, so a drain in a Python app that is not declared is not counted: T2 FAIL and the T3 sum assume none. The detail line and the `none declared` wording say so.

### What was not measured, and the expectation behind it

- **More than two workers.** `-w 1` and `-w 2` were run and gave the same ceilings; larger counts are not measured, and `graceful_timeout` is a timer of gunicorn's main process, so no difference is expected.
- **Other signals, other platforms.** SIGQUIT, SIGINT and SIGHUP were not measured; one machine (macOS arm64); the Linux container case is expected to match because the timers are in the servers' own code.
- **HTTP protocol of uvicorn.** The shutdown runs were made on a plain install (h11). The shutdown timer is in uvicorn's server rather than in the protocol, so httptools is expected to behave the same; unlike keep-alive (B2), this was not measured, and no gate keys on it.
- **A preStop hook's real behaviour, and a pod's actual kill.** The Kubernetes behaviour (the grace countdown starts before the preStop hook, SIGKILL after it) is documented, not observed.

### Inline waiver comments

A real YAML comment that starts `# tripcurve:` in a YAML file read is extracted raw, with its file and line, and nothing is validated; the waiver reader of bolt B6 judges it and lists a malformed one by its line. Text inside a quoted or block scalar is not a comment. Terraform comments come with the Terraform reader (B5); comments in standard input are not read. The collector walks the parser's token tree with an explicit stack and is linear in the file.

### Review fixes (B4 adversarial review)

- **A drain the source shows counts only when the search for drains was complete, or the user declares the drain**. With unread code left, a handler there could stop the server sooner. A preStop delay still gives T2 PASS on its own (it does not depend on the source); T3 is UNRESOLVED when the drain term is not established ("drain not established; grace cannot be checked").
- **A Python server's drain is counted as 0 s in T3, and that is an assumption**: "In-process drains of Python servers are not read; counted as 0 s." is listed whenever a T3 verdict used it.
- **Shutdown libraries and side-effect imports make the drain search incomplete**, never T1: an import, `require` or `import()` of a package in the list in `src/parse/node/shutdown-libraries.ts` (`close-with-grace`, `http-terminator`, `stoppable`, `http-graceful-shutdown`, `fastify-graceful-shutdown`, `graceful-shutdown`, `node-graceful-shutdown`, `death`, `signal-exit`, `exit-hook`, `async-exit-hook`; subpaths too) gives "a shutdown library is imported whose drain tripcurve does not read". A bare `import 'pkg';` (or `require('pkg');` as a whole statement) of a non-local, non-built-in package gives "a package is imported only for its side effects, which may include signal handlers". `@godaddy/terminus` and `lightship` are read and are not in the list. A server handed to anything but `createTerminus` from a module that was not read also makes the drain search incomplete. The list is a fixed list, not a guess at what else might exist: a library not in it is still not read (see "Not read, so not found").
- **A top-level `process.exit(...)` or `throw` before the first `listen` makes what follows a dead path** (minor 5): the drains and the T1 settings after it are not shown to run, so they are UNRESOLVED.
- **Sub-millisecond precision** (minor 2): the time to be covered (preStop, drain, L) rounds UP to a whole millisecond and the grace period rounds DOWN, so `longest_request_s: 25.0004` against a grace of 26 s is not enough.
- **A drain that was read and is 0 s** prints "a drain of 0 s was found at <place>" in a T2 FAIL, not "read for Node source only" (minor 1).
- **Pins** (minor 4): a `package-lock.json` entry whose `name` is not the package (an npm alias) is UNRESOLVED; a zero-padded version (`9.1.01`) is not a version.
- **Kustomize overlays are not read** (minor 8): `kustomization.yaml` patches, such as one that adds a preStop or changes `terminationGracePeriodSeconds`, are not applied; tripcurve reads the manifests as written (render with `kustomize build` and pipe the result in). This is outside B4.
- **Valid-but-unreachable guard:** `valueMs` refuses a negative or fractional-millisecond value. No file can produce one (the readers reject negatives and the config reader refuses them), so it is tested directly, not end to end.

### Allow-list for the Node "no drain" claim (B4 second review, N1 and N2)

- **N1.** "No drain found" for a Node workload is an absence claim, and any imported package runs its module code, which could register a SIGTERM handler. So the drain search is complete only if every import, `require`, `import()` and re-export in every file read is a local file that was read, a Node built-in (`node:*` or a built-in module name), or type-only (`import type`, `export type`). Any other package (a side-effect import, an unused default or named import, `import {} from 'pkg'`, `export * from 'pkg'`) makes it incomplete: T2 is UNRESOLVED with "a package is imported whose code may register shutdown handlers; declare drain.in_process_s or add a preStop" (the more specific reasons for a listed shutdown library or a side-effect import are kept). `@godaddy/terminus` and `lightship` are read forms and do not make it incomplete by themselves. T1 has its own allow-list and is unchanged. **Cost:** a Node T2 FAIL now appears only for apps that import nothing but built-ins and local files; an app that uses Express, for instance, is UNRESOLVED unless it has a preStop delay or a declared drain (a preStop PASS does not depend on the search).
- **N2.** The terminus exemption covers only the exact `createTerminus(server, ...)` call. Any other use of the listening server variable than as the receiver of a property access (`server.on`, `server.close`), its own declaration or assignment, or the first argument of `createTerminus` (an alias, a pass to any function, an object, an export, a return) makes the drain search incomplete.

## Terraform and rule T4 (B5, 2026-11-12)

Evidence: `docs/lookups-b5.txt` (the dated lookups of 2026-11-12, including the `aws_lb` documentation page read on that day). `test/kb/terraform-evidence.test.ts` checks every Terraform knowledge-base entry against it word for word.

### What is read (an allow-list; nothing else counts)

- **Types and attributes.** `resource "<type>" "<name>" { ... }` for four types and eight attributes: `aws_lb` (`idle_timeout`, and `name` and `load_balancer_type` for the by-name link and the application check), `aws_sqs_queue` (`visibility_timeout_seconds`), `aws_lambda_function` (`timeout`), `aws_lambda_event_source_mapping` (`maximum_batching_window_in_seconds`, `event_source_arn`, `function_name`). `name` and `load_balancer_type` are two reads beyond the four values the load balancer and queue links compare; the link by name and the "only valid for application load balancers" rule need them.
- **Forms.** An integer literal, a plain string literal (no `\`, `$` or `%`), or a reference of exactly the shape `<type>.<name>.<attribute>` (`aws_sqs_queue.<n>.arn`; `aws_lambda_function.<n>.arn`, `.function_name` or `.qualified_arn`). A variable, a local, an expression other than the integer arithmetic below, a function call, a conditional, `null`, a fraction, a negative number, a heredoc, an index, a module output or a `"${...}"` template is UNRESOLVED. An integer outside the documented range (0 to 43200 s, 1 to 900 s, 0 to 300 s, and 1 to 4000 s for the ALB) is UNRESOLVED too. The ranges are from the lookups, and a test checks them.
- **Integer arithmetic on literals (B17).** A numeric attribute may be written as an expression made only of decimal integer literals (`0`, or a digit 1 to 9 and more digits, at most 15 digits), `+`, `-`, `*` and parentheses, on one line (`visibility_timeout_seconds = 60 + (30 * 6)` is 240). `*` binds tighter than `+` and `-`, and operators of one level group left to right, as in HCL's specification (`docs/lookups-b17.txt`, read 2026-11-12). It is read exactly or not at all: no `/` or `%` (Terraform division gives a number that is not a whole number), no unary sign, no variable, function, string, point, exponent or prefix, no leading zero (HCL reads `010` as ten; refusing it errs toward UNRESOLVED), no line end and no comment inside the expression (HCL ignores both inside parentheses, but the lexer keeps no comments, so they are refused), at most 64 tokens and 8 levels of parentheses (checked before parsing, so a hostile text costs work in proportion to 64), and every literal and every intermediate value at most 2^53 - 1 so that HCL's arithmetic is exact on the same numbers. The result must be a whole number inside the attribute's documented range, or the value is UNRESOLVED. The report shows the computation as input text beside the number (`visibility 240 s = "60 + (30 * 6)" at "sqs.tf":4`; JSON: an `expression` field on the chain value). Terraform JSON has no equivalent form short of a `"${...}"` string, which is UNRESOLVED, so JSON stays literal-only.
- **A root that is one Terraform file (review of B17).** `tripcurve path/to/all.tf` reads that file only, not the rest of its folder, which Terraform reads as one module (a sibling `override.tf` could change any value). Every Terraform resource read that way is UNRESOLVED with `only one file of the module was given; check the folder`, for FAIL as well as PASS: a sibling could change a value either way. Run on the folder to get a verdict.
- **A block that is not exactly one instance with the attributes it shows has every value unresolved:** `count`, `for_each`, a `dynamic` block, a `lifecycle` block holding anything but `create_before_destroy` and `prevent_destroy` set to `true` or `false` (so `ignore_changes` counts), an attribute written twice, and a resource that an override file (`override.tf`, `*_override.tf`, and the `.json` forms) of the same folder also names. An override file that cannot be read makes every resource of its folder unresolved. Unknown attributes and other nested blocks are skipped: they cannot change a top-level attribute.
- **A file that cannot be read yields no resource at all.** An unterminated string, heredoc, comment or bracket, a mismatched bracket, a character HCL does not allow (a non-ASCII identifier included), a top-level assignment, or a `resource` with other than two labels. It is listed under "Files not checked" (reason `terraform-unreadable`), the run is not clean, and no claim of absence (see below) is made. A heredoc closes exactly as HCL's own scanner closes it (`scan_tokens.rl`, `heredocLiteralEOL`): at the start of a line, when the whole line trimmed of Go white space (`bytes.TrimSpace`: spaces, tabs, carriage returns, a no-break space and the other Unicode spaces, but not U+FEFF) equals the marker, for `<<ID` and `<<-ID` alike, and never after a `${ }` or `%{ }` on the same line. A heredoc the text never closes that way ends unterminated and the file is unreadable. (the first version took leading space only for `<<-` and no trailing space, so an indented or space-padded close was missed and the attributes after it were swallowed.) The same audit made a carriage return that is not part of `\r\n` (in code, inside a quoted string, or after a backslash), a vertical tab, a form feed, a no-break space in code, a template strip marker (`${~`, `~}`) and a single quote make the file unreadable, as HCL's scanner rejects them.
- **Duplicates and ignored files.** The same `(folder, type, name)` in two files of one folder (`.tf` and `.tf.json` included) is a resource Terraform rejects, so every instance is UNRESOLVED ("the same Terraform resource is declared twice"); the same name in two folders is two modules. A `.tf` or `.tf.json` whose name starts with a dot (or is an editor's `#name#` file) is not read and not reported, as Terraform ignores it. A file named `#name.tf` is read, because Terraform reads it.
- **The lexer never recurses** (nesting is a byte stack the size of the text, tokens are typed arrays), so work and memory are linear in the file (a test checks the scaling). Over 5 MB: intake refuses the file as for any other file, and the Terraform read is marked incomplete.
- **`*.tf.json`** is read as JSON (through the YAML parser, so every value keeps its line; JSON that is not YAML-compatible, such as duplicate keys, is reported as `YAML syntax error`, which is a known imprecise wording for a JSON file). The same attributes, with the same count/for_each/dynamic/lifecycle rules; a reference is the string `"${type.name.attr}"` and nothing else.
- **`terraform show -json`** (a plan or a state; as a file named as the path, or on stdin): numbers and names are read from `planned_values` (or `values`), where Terraform has applied defaults, and a missing value is UNRESOLVED, never a default. References are read only from `configuration`, as the exact `references` list of one attribute (`X.arn` and `X`). A state has no `configuration`, so its mappings are not linked. Resources in child modules are not read; a resource with an `index` is UNRESOLVED. Known limit: in `configuration`, an expression that mixes a reference with other text (`lower(aws_sqs_queue.q.arn)`) gives the same `references` list as the bare reference, and is read as the bare reference. A `.json` file met while walking a tree is NOT sniffed (a lock file is never read for it); only the one file named as the path is.
- **The `.terraform` folder is never walked** (downloaded modules and providers), like `node_modules`.
- **Not read:** `aws_alb` (the older alias of `aws_lb`), SAM and CloudFormation (bolt B12), module sources, `-var` files and workspaces. A value that comes from them is an expression, so it is UNRESOLVED.

### Defaults when an attribute is absent

- **`aws_sqs_queue.visibility_timeout_seconds` (30 s), `aws_lambda_function.timeout` (3 s) and `aws_lb.idle_timeout` (60 s; an absent `load_balancer_type` is the documented `application`)** follow from the file: the provider documents a default and Terraform applies and reconciles it. Basis `documented`, the "not measurable locally" reason form, and they may give PASS or FAIL. The provider source (read 2026-11-12) has a schema `Default` for all three: `internal/service/sqs/queue.go`, `internal/service/lambda/function.go` and `internal/service/elbv2/load_balancer.go`. The `aws_lb` default carries `DiffSuppressFunc: suppressIfLBTypeNot(Application)`, so it is reconciled only on application load balancers: tripcurve uses it only when `load_balancer_type` is application or absent (absent is the documented `application`). A test checks that an entry claims a schema default exactly when its source line is in `docs/lookups-b5.txt`.
- **`maximum_batching_window_in_seconds` has no provider default,** so its absence does NOT establish 0 (AWS applies 0 for SQS at create; Terraform does not manage it afterwards). It is used as the ASSUMED value 0 s, and the assumption is listed once. A window is 0 s or more (documented range 0 to 300 s), so it can only RAISE the need, and T4 (B17) therefore has two cases. Visibility below 6 x the function timeout is a FAIL whatever the window is: the result says `the batching window is not set, and any window only raises the need` (`is not known` for a window that is a variable or out of range), and its chain holds only the visibility and the timeout, never the assumed value. Visibility at or above 6 x the timeout needs the window to settle: T4 is UNRESOLVED, prints `assumed 0 s` and `T4 would pass` (only when the other two inputs are established), and never PASS. Before B17 both cases were UNRESOLVED.

### The link between mapping, queue and function

A mapping links to its queue and function only by a reference that matches exactly one resource of the same FOLDER (B17; before it was the same file). Terraform reads every `.tf` and `.tf.json` file of one directory as one module ("effectively treating the entire module as a single document"), and "nested directories are treated as completely separate modules" (Terraform documentation, "Files and configuration structure", read 2026-11-12; `docs/lookups-b17.txt`). So:

- A reference links within its own folder, across `.tf` and `.tf.json` files. It never links into a subfolder, a parent folder, a sibling folder or a `module` block, and a `module` output is not a reference tripcurve follows.
- Everything that made a value UNRESOLVED still does: the same address in two files of the folder (every instance is UNRESOLVED), a variable, a local, a function, `count`, `for_each`, a `dynamic` block, an unread `lifecycle` setting.
- An override file (`override.tf`, `*_override.tf` and the `.json` forms) merges into the resource of the same address in its folder ("an attribute argument within an override block replaces any argument of the same name in the original block"), so every block of that address in that folder is UNRESOLVED "an override file changes this resource" (this is what B5 already did; B17 only made the folder the unit of the link). An override in another folder changes nothing here. An override file that cannot be read makes every resource of its folder UNRESOLVED.
- A Terraform file of the folder that was not read (unreadable, over the size limit, or not a syntax the reader takes) is listed under "Files not checked" and the run is not clean. A queue or function that is not found in such a folder is reported as `a file of the same folder was not read, so what the mapping names may be declared there`, not as absent. A queue found exactly once is still linked: a second declaration of its address in the unread file would be a configuration Terraform rejects, so no deployed value can differ.
- A plan document (`terraform show -json`) and a SAM or CloudFormation template are one module each, as before.
- A literal ARN, a name, a variable, a stream (`aws_kinesis_stream`, `aws_dynamodb_table`) or an unreadable block gives UNRESOLVED with a fixed reason and `declare` text. A mapping whose event source is a stream is therefore UNRESOLVED, not N/A: that is the conservative reading, because N/A would let a run exit 0 on an ARN tripcurve cannot follow; this is listed as a question for the maintainer.

### The Terraform load balancer links

- **Declared:** `load_balancer: {terraform: aws_lb.<name>}` links to the `aws_lb` of that resource name when exactly one was read (none: UNRESOLVED, with "a Terraform file could not be read" when one was not read; several: UNRESOLVED). It is established; its idle value (a literal, or the documented default) may give PASS or FAIL. When the Ingress annotation also gives an idle value, the two must agree or the result is UNRESOLVED with both shown.
- **By name:** an Ingress `load-balancer-name` annotation equal to the literal `name` of exactly one `aws_lb` links with the basis `assumed`: the value is read and shown, and the assumption line is printed, but T1 is never PASS and never FAIL on it. The controller applies the name only when it creates a load balancer, and a Terraform-owned one is normally joined by TargetGroupBinding, which is not read. "Exactly one" is a claim of absence, so it needs: every Terraform input read (no unreadable or over-size file), and every `aws_lb` to have a literal name (one with a variable, no name, or `count` blocks the claim). Only a name of letters, digits and hyphens (up to 64) is linked, because the assumption line quotes it and a name with a space could wrap; AWS's own name rules were not looked up. An Ingress annotation that gives an idle value is established and the by-name link is not used (a differing Terraform value is UNRESOLVED, both shown). A declared link outranks a by-name link. A shared ALB (an IngressGroup, or a repeated `load-balancer-name`) stays UNRESOLVED unless a declaration states the value.
- **The line of the `name`** in the assumption is the line of the `name` attribute of the `aws_lb`.

### Inline waiver comments

`#` and `//` comments that start `tripcurve:` in a `*.tf` file are read raw, with their lines, by the Terraform lexer (so text inside a string or heredoc is not one, and a `/* */` comment is not read); B6 judges them (see "Waivers and `--explain`" below), and `--explain T4` with its cdk-nag credit is B6 too.

## Waivers and `--explain` (B6, 2026-11-12)

Sources: the requirements on waivers, the report mockups for the four waiver states and `--explain`, and the interaction spec. Every reading below is a choice between things the documents leave open; each names its source.

### What a waiver is, and the one validator

- **One validator.** `src/waive/` is the only place a waiver is judged. The config reader and the comment scanners hand over raw records. A waiver ends in exactly one state: `applied`, `expired`, `unmatched` or `invalid`.
- **Two forms.** An inline comment, exactly `tripcurve: ignore <RULE> reason="<text>" until=<YYYY-MM-DD>` after `#` (YAML, Terraform) or `//` (Terraform), in that order; or a `waive:` entry with the keys `rule`, `workload`, `reason`, `until` and the optional `namespace` and `kind` (a kind from the fixed list). The reason follows YAML double-quote escapes (`\"`, `\\`, `\n`, `\t`, `\xNN`, `\uXXXX` and the rest of YAML's table); an unknown escape, an unclosed quote or text after the date makes the waiver invalid ("not in the form ..."). Fields in another order are invalid, not guessed at (the design says "exactly").
- **Invalid.** A text that does not fit the form, a missing reason, or one with no visible character (blanks, zero-width characters, controls: it needs a letter, digit, punctuation mark or symbol), a reason over 200 characters (counted as characters, so an astral character is one), a missing or impossible date (the calendar is checked, so `2027-02-30` is invalid; years 0001 to 9999), an unknown rule, an unknown field in an entry, or a workload that was not read. The FIRST problem found is named, in this order: form, rule, reason, date, workload. An invalid waiver suppresses nothing, never stops the run (a decision that overrides the earlier "configuration error" option) and is counted under unresolved (file).
- **A waiver in a `waive:` entry that is not a mapping** (`- "text"`) is listed as invalid too, with "is not an entry with rule, workload, reason and until". A `waive:` key whose value is not a list at all (a scalar, a mapping, nothing) is one listed invalid waiver, "waive must be a list of entries", and the run goes on. A repeated key inside an entry still makes the file unreadable YAML (a configuration error, as for any repeated key), and the error now names the key.
- **`until` has no upper bound**; `9999-12-31` is valid. The visibility is the control: every waiver prints with its date and reason.

### Which finding a waiver covers

- **A waiver names one rule and one workload.** It covers FAIL, WARN, UNRESOLVED, VERSION-DEPENDENT and NOT EVALUATED; never PASS or N/A. A waiver whose rule has a PASS or N/A for that workload, or no result at all (T4 on a Deployment), is `unmatched`.
- **A config waiver finds its workload by name**, then by `namespace` and `kind` when it gives them. A name that two workloads share (two namespaces, or a Deployment and a StatefulSet) is invalid ("names more than one workload; give its namespace or kind"). A workload that was read but has no result (not checked) is `unmatched`, not unknown. An event source mapping is named by its resource name (T4).
- **An inline waiver attaches by line** ("the workload or resource whose block contains the comment line"; the build brief's "source line or the next line" was not used because the quoted wording is the approved text). The block of a YAML object is its document: every line from the end of the document above it (the start of the file for the first) to the line before the next `---`, comments included, so a comment above a `---` belongs to the document above it and one below it to the document below. In a `kind: List` each item is a block, and the header lines before the first item belong to none. The block of a Terraform resource is the lines from its header to its closing brace. A comment that sits BETWEEN two blocks is invalid too ("sits between two documents (or items); put it inside the block it waives"): in the run of blank and comment-only lines directly before a `---` that starts the next document, or directly before the `- ` of the next List item at that item's indent or less (a deeper-indented comment is still the previous item's content). A comment at the very end of the last document has nothing after it and stays in its block. A comment outside every block (in a Service, in `tripcurve.yaml`, between Terraform resources, in a YAML document that did not parse) is invalid ("is not inside the block of a workload or event source mapping that was checked"). A comment in a Terraform queue or function block is NOT in the block of the mapping whose T4 it concerns: it attaches only to the mapping resource itself.
- **Comments are read in every YAML file intake finds**. A `.yaml` or `.yml` file that tripcurve does not otherwise read (a Helm `values.yaml`, a non-Kubernetes file, a comment-only file) is still scanned for waiver comments, within the same file size limit and root confinement; each one is listed as invalid, outside every block, and counted unresolved (file). A file in a skipped folder (`node_modules`, `.git`, `.terraform`), a file over the limit (already listed as unchecked) and a file that is not YAML by name are not scanned. Comments in standard input are still not read.
- **Two waivers for one finding cover neither.** Which would win is not written in any file, so both are listed as invalid ("covers a finding that another waiver also covers") and the finding keeps its real result. This also holds when one of them has expired.
- **A waiver never changes a rule.** T3 stays NOT EVALUATED when T2 failed, waived or not; the arithmetic of a rule never sees a waiver.

### Expiry and the date

- **Through the date, inclusive, in UTC**: `until=2027-01-31` applies on 2027-01-31 and has expired on 2027-02-01. An expired waiver changes nothing: the finding keeps its kind, and under it the report says `waiver expired on <date>`, then the quoted reason and where it is written. It is not counted as unresolved: the finding it no longer covers already makes the run unclean.
- **The date is an input**. The command reads the clock once, in `src/cli/clock.ts`, the only place that does, and passes the UTC date down; the library `check()` takes `today` (default: today's UTC date; a value that is not a date throws `TypeError`). A test scans every other source file for a clock read. `assembleReport` without a valid date lists every waiver as invalid ("cannot be judged because the date of the run is not known") rather than judging against a guess.
- **A waiver that has expired and whose finding is now a PASS** is `unmatched` (it names nothing it could cover), like any stale waiver.

### What the report prints

- **WAIVED** is the one line form: `WAIVED <rule>  (was <KIND>: <headline>) until <date>: reason "<reason>" from <source>`, wrapped at spaces onto lines indented 11 columns; the word `reason` stays with its quoted text. A reason that does not fit on the line is printed whole, never cut (it is what a reviewer reads; 200 characters at most): after the `until` line, one `reason (part k of n) "<piece>"` line per piece of up to 44 escaped characters (a piece never splits an escape), then a `from <source>` line. The fixed words keep a line from starting with quoted input. It carries no chain or declare lines (the line repeats what it covers); `--verbose` adds the chain.
- **`Waivers not applied`** lists each unmatched waiver (`no finding for rule T2 on workload "admin" matches the waiver at "tripcurve.yaml":3`, the unmatched-waiver case) and each invalid one (`waiver "<text>" at <source> <what is wrong>; it suppresses nothing`, the invalid-waiver case) as `UNRESOLVED (file)`. The text is quoted: an inline comment without its comment mark, an entry on one line (its line breaks and indentation read as single spaces). The first 50 are listed and the rest are counted in one line; the summary counts every one.
- **Closing lines** are wrapped greedily at 80 columns (the same rule as every other line), so `No failures: 3 passed, 3 waived (expiring ...), 0` can end a line and `not applicable.` start the next; the waiver mockup shows a hand wrap at the comma.
- **Exit codes** are RunSummarizer's and PipelineRunner's, unchanged: 0 for Clean, `No failures:` (every waiver applied) and `No checks apply:`; 1 for any unwaived non-pass result, an unchecked file, or an unmatched, invalid or expired waiver; 2 for nothing checked, a usage error or a configuration error; 3 for an internal error.
- **Cost.** Waivers are matched with indexes and binary searches, so a file full of them is read in linear time (a scaling test, and a test with 20,000 invalid entries).

### `--explain <rule>`

- **What it prints:** the rule, its vendor quotes with their links and the date each was read, every knowledge-base entry of the rule's subjects with its range, value, basis words and date (generated from the knowledge-base data, so it cannot drift; a test changes an entry and sees the text change), and when the rule does not apply or cannot decide. T4 carries a Credit section: the cdk-nag rule `LambdaEventSourceSQSVisibilityTimeout` (added 2024-11-01, PR #1813) and cfn-lint E3505, with their links, and says T4 is not new.
- **Dates of the quotes.** The ALB and EKS quotes are those of `docs/research.md` (sections 1 and 7). The notes give no day for each quote, only that the sweep ran on 2026-10-29 with re-checks through 2026-11-02, so the text prints "read 2026-10-29 to 2026-11-02, research notes", not one day; the Kubernetes and gunicorn quotes are from `measure/results/2026-11-11-lookups-b4.txt` (2026-11-12) and the Lambda quote from `docs/lookups-b5.txt` (2026-11-12). A test checks each quote and link against those files.
- **An unknown rule** prints `tripcurve: unknown rule. Rules are T1, T2, T3 and T4. See --help.` on stderr and exits 2. It does not echo the rule: the requirements ask for a fixed message and the B6 brief for no input text in explain output. The report mockup shows the rule quoted; echoing it through SafeText is a one-line change if the maintainer prefers it.
- **`--explain` with a path** is a usage error. Other flags are not looked at.
- **No input reaches it.** It reads no file and takes only a rule id; the explain table is shipped data beside the rules (`src/evaluate/explain-entries.ts`), and the text is built in `src/report/explain.ts`.


## JSON and SARIF output (B7, 2026-11-12)

### SARIF validation: is not met as written (the fallback)

The acceptance criterion says the SARIF output "validates against the repo-kept SARIF 2.1.0 schema", and that wording stands and is not changed here. tripcurve keeps no copy of that schema, which deviates from the criterion. The build plan (outside this repository) gives a fallback, which applies: "validate against a locally written subset only if the terms forbid vendoring, and say so; maintainer decides". The terms forbid it for this project:

- The schema file lives in `oasis-tcs/sarif-spec`, whose licence file (read 2026-11-12) says the content "is governed by the OASIS policies, including the Intellectual Property Rights (IPR) Policy ... (viz, RF on RAND Terms Mode)". That is not a standard permissive licence, and the project rule is to copy files only from permissive ones. The GitHub API reports the licence as NOASSERTION. The licence file was read again on 2026-11-13 (HTTP 200; `docs/lookups-b16.txt`). That is not MIT, Apache-2.0 or BSD, and the project's Forbidden rule allows copying third-party files only under those licences.
- A full JSON Schema validator would be a new dependency, which the maintainer's rules forbid.

So what `npm run verify` runs in place of the repo-kept schema is `test/support/sarif-validate.ts`, a hand-written validator for the subset of SARIF 2.1.0 that tripcurve emits:

- **What it checks:** `version`, `runs`, `originalUriBaseIds`, `tool.driver.name`, the rules (`id`, `shortDescription.text`, `help.text`), and for each result `ruleId` (which must be one of `tool.driver.rules`), `ruleIndex` (an integer of 0 or more, naming that rule), a required `level`, `message.text` (and `markdown`, a non-empty string), `locations[].physicalLocation.artifactLocation.uri` (a relative reference with a declared `uriBaseId`, or a `file:` URI without one, percent-encoded), `region.startLine` and `startColumn` (1 or more), and `suppressions[]` (`kind`, `status`, `justification`, no repeats), plus the types of every `properties` bag.
- **Closed property sets (review of B7, m1):** for every object type tripcurve writes (log, run, tool, driver, rule, message, result, location, physicalLocation, artifactLocation, region, suppression, and the `originalUriBaseIds` entries) the validator lists the properties it may carry, and any other key is a problem. A misspelt key (`levle`, `rulez`, `startLineX`, `suppression`) therefore fails instead of being ignored. The `properties` bags stay open, as the spec says (3.8.1). `level` is required on every result: the spec's default for an absent level depends on `kind`, and a reader that gates on level must never guess.
- **Where each check comes from:** every check cites its section of "Static Analysis Results Interchange Format (SARIF) Version 2.1.0, Errata 01" (OASIS Standard; https://docs.oasis-open.org/sarif/sarif/v2.1.0/errata01/os/sarif-v2.1.0-errata01-os-complete.html) with the spec's words quoted, read 2026-11-12. The `uri` checks also cite RFC 3986 section 4.2 (https://www.rfc-editor.org/rfc/rfc3986.txt, read 2026-11-12).
- **How it is tested:** every SARIF golden and every document the SARIF tests and the property test produce passes it, and `test/report/sarif-validate.test.ts` shows it fails on more than 100 kinds of broken document.
- **What it is not:** it does not check what tripcurve never writes (for example `codeFlows`, `fixes`, `taxonomies`), and it is not the official schema. A SARIF consumer that validates against the official schema is the real test, and that happens only after the maintainer's go (no upload before then).

**Decided (2026-11-12): the official schema is not vendored, and this is a recorded deviation from the acceptance criterion.** `npm run verify` keeps this subset validator in its place. The v0.1 check is the dated one-off validation against the official schema. As a dated one-off check in B16 (not part of `npm run verify`), the official SARIF 2.1.0 JSON schema, downloaded read-only into a scratch folder, validated every `test/golden/report-*.sarif.txt` and the SARIF of `demo/` and `demo-fixed/`, and rejected four deliberately broken documents; the URL, SHA-256, script and output are in `docs/release-check-run-b16.txt`. The schema declares JSON Schema draft-04, so the check used `ajv-draft-04` with `ajv-formats`; none of them is a dependency of tripcurve. Repeat the one-off check on the day of the maintainer's go.

### Where a SARIF result is located

The SARIF contract names `locations[0].physicalLocation` and `region.startLine` and does not say which line. The renderer uses one rule:

1. the first value of the result's chain that was read from the same file as the workload (for `web` T1, the image at `"k8s/web.yaml":17`);
2. otherwise the workload's own object in its file (the `kind:` line, or the `resource` line of a Terraform mapping).

A value read from another file (the Ingress, `"k8s/ingress.yaml":9`) is never the location, because the annotation would then land on a file the finding is not about; the file is in the JSON chain. Paths are the paths intake reports, relative to the checked root: the root itself is not a repository root unless `tripcurve` is run from it.

- **Standard input** has no file, so a result from it has no `physicalLocation`, and `properties.tripcurve.source` says `<stdin> document n, line m`. GitHub code scanning cannot show such a result.
- **The root.** The nothing-checked and run-level results are located at the checked root, which is the `SRCROOT` base itself: `uri: "."`, `uriBaseId: "SRCROOT"`, whatever path was typed (the message quotes what was typed). They have no `region`, which SARIF allows: `startLine` is required only when a region is given (3.30.5), and a result for the run as a whole has no line.
- **No `helpUri`.** The SARIF design lists a `helpUri` for each rule. tripcurve has no published documentation address yet, so there is no address to put there and none is invented. Each rule carries `help.text` instead ("Run `tripcurve --explain T1` ..."; SARIF 3.49.13 says `help` is for the case where "help information is not available at a URI"). The maintainer can add the URI at release.

### What the JSON adds to the design

The JSON contract is the authority. The fields below are additions that a consumer may ignore (the contract says "unknown fields must be ignored by consumers"):

- `workloads[].namespace`, `workloads[].line`, `workloads[].document` (standard input), `workloads[].helmSource`;
- on a chain entry: `valueType` (`value`, `text`, `unresolved` or `note`), `detail`, `confidence`, `decidedBy`, `declareHint`;
- on a result: `originalKind`, `declare`, `decidingNote`, `expiredWaiver`;
- `waivers[].mechanism`, `notChecked[].reasonCode`, `unchecked[].reasonCode`, `configErrors[].reasonCode`, `expected` and `workload`;
- `checked.documents` for standard input.

Every printed string of input text is an ordinary JSON string. The writer escapes every character above `~` as `\uXXXX`, so the document is plain ASCII and no control, bidirectional or invisible character from an input reaches a reader's screen raw. A lone surrogate becomes U+FFFD (SafeText's data mode), and nothing is cut: a long name is whole.


### Review of B7: what changed in the SARIF document

- **A run that is not clean always has an unsuppressed `error` or `warning`.** NOT EVALUATED stays a `note` (as approved), so a run whose only unsuppressed result is a note (T1 and T2 waived, T3 NOT EVALUATED) would pass a gate that reads only `error` and `warning`. When `clean` is false and no such result exists, one `warning` is added under the rule `tripcurve-run`, located at the checked root: `the run is not clean: 1 not evaluated; see the run properties`, with the unclean counts in the order of the closing line. It is never added to a clean run, and never when a file result, an unmatched or invalid waiver, a configuration error, the nothing-checked result or an unsuppressed error or warning is already there. The property test checks this on 2,500 reports.
- **Messages cannot hold a link or a placeholder.** A SARIF message is plain text, and an input name such as `[pwn](https://evil.example/x)` in it would be an embedded link. SARIF 3.11.6 (read 2026-11-12): "Within a plain text message (3.11.3), an embedded link SHALL conform to the following syntax ... embedded link = "[", link text, "](", link destination, ")"" and "Literal square brackets (" [ " and " ] ") in the link text of a plain text message SHALL be escaped with a backslash". SARIF 3.11.5 (same date): "Within both plain text and formatted message strings, the characters " { " and " } " SHALL be represented by the character sequences " {{ " and " }} "". So every message is written through `escapeMessage`: `[` and `]` become `\[` and `\]`, `{` and `}` become `{{` and `}}`. SafeText already doubles a backslash in a quoted name, so an escape is never cancelled. Braces are doubled as 3.11.5 requires; whether GitHub's viewer decodes `{{` back to `{` is unverified. A configuration key such as `workloads[0].longest_request_s` therefore reads `workloads\[0\].longest_request_s` in a SARIF message (and is unchanged in the human report and in JSON).
- **A suppression carries its expiry (m2).** `suppressions[].properties.tripcurve` holds `until`, `mechanism` and the waiver's `source`, so a consumer that reads only SARIF sees when the waiver ends.
- **Everything that was not checked is a `note` (m4; second review m-D).** One result per item of `notChecked` (a workload with no load balancer, an Ingress that is not an ALB Ingress, a kind that is not checked) under the rule `tripcurve-not-checked`, located at its file, so the number of these results equals `properties.tripcurve.notChecked`. A note does not fail a gate and the run stays Clean; a reader that looks only at results can still see that the workload was not looked at.
- **A result with no level of its own is a warning (m6).** Any finding that is not PASS or N/A and has no level is a `warning`. A WAIVED finding is suppressed only when it holds both its original kind and its waiver; the level always follows the original kind (`FAIL` stays `error`), and a WAIVED finding with no original kind is a `warning`.
- **URIs have a base (m8).** SARIF 3.4.4 (read 2026-11-12): an artifactLocation whose `uri` is a relative reference "SHOULD contain a property named uriBaseId", and "If the uri property contains an absolute URI, the uriBaseId property SHALL be absent". SARIF 3.14.14: a run MAY contain `originalUriBaseIds`, and its `uri` "MAY be omitted" when it would be absolute, "to produce deterministic output ... by avoiding path names that differ depending on the machine". Every relative `uri` therefore has `uriBaseId: "SRCROOT"`, and the run declares `SRCROOT` with a description and no `uri`, so no machine path is in the log. (The id is the bare word `SRCROOT`, as in the spec's own example; `%SRCROOT%` is a different convention.) **How to run it:** the paths are relative to the directory that was checked, so a CI job should run `tripcurve . --format sarif` from the repository root; then `SRCROOT` is the repository root and GitHub resolves each path against it. Run from a subdirectory, or with another path, the paths are relative to that directory and do not match the repository.
- **`--explain` prints text only (m7).** `--explain` with `--format json` or `--format sarif` is a usage error (exit 2, "--explain prints text only"), so a consumer never gets text where it expects its format.

### A configuration file that cannot be read (review of B7, m3)

The requirements say an invalid configuration file prints the config-error case, checks nothing and exits 2, and a file that intake could not parse is also an unchecked file. The documents do not say that the human report may leave the unchecked file out, and JSON and SARIF listed it, so the three formats disagreed. Now all three show both: the human report prints `Files not checked` after the configuration errors. An error about the whole file no longer names the placeholder key `(file)`; it says `the config file could not be read`, `the config file is not a mapping of keys`, or `the config file has more than one document`. JSON adds `wholeFile` (`unreadable`, `not-a-mapping` or `several-documents`) to such an error; its `reasonCode` is still `invalid-schema`. The human golden of the config-error case is unchanged (it has no unchecked file).

### NoChecksApply has no file that produces it

T2 and T3 never return N/A, so a workload that is behind a load balancer always has a T2 result, and no set of files gives a run whose only results are N/A. The JSON and SARIF goldens for that outcome (`report-noapply`) are built from a Report, in `test/report/noapply-golden.test.ts`.

### The summary on the config-error case stop

"on the config-error case stop the document has empty `workloads`, `configErrors` filled, every count 0, `outcome: ConfigError`, `clean: false` and `exitCode: 2`" (the report model says the same: "zero counts"). No rule ran, so the invariant "`unresolved` = UNRESOLVED results + unchecked files + waivers not applied" holds on every outcome except `ConfigError`, where every count is 0. An unchecked file on the config-error case stop (an unreadable `tripcurve.yaml`, or `--config` naming a file that does not exist) is listed under `unchecked` in JSON, as a `tripcurve-file` warning in SARIF and under `Files not checked` in the human report, but it is not counted. The human the config-error case output prints no count (`Nothing was checked.`).

## The timed check and the demo (B10, 2026-11-12)

`npm run verify` ends with a labelled step, `npm run timed-check` (`scripts/timed-check.mjs`), after `npm run build`. It runs the built command twice over and takes the fastest of 3 runs of each (noise only adds time):

| What is timed | Budget (maintainer-confirmed) | Measured, fastest of 3 |
|---|---|---|
| `tripcurve .` inside `demo/` (14 files) | under 2 s | 0.23 s, 0.23 s |
| `tripcurve .` over a generated 1,000-file tree | under 30 s | 1.75 s, 1.77 s |

The two figures in each row are from two full `npm run verify` runs on 2026-11-12 (the three runs inside them were 0.23, 0.23, 0.23 s both times for the demo, and 1.75, 1.86, 1.76 s and 1.80, 1.77, 1.78 s for the tree). Machine: Apple Mac17,3 (`sysctl -n hw.model`), Apple M5 (`sysctl -n machdep.cpu.brand_string`), 10 cores, Node v22.23.2, load average (1 minute) 1.51 just before the first run and 7.90 just after the second, and the two runs gave the same times to 0.1 s. Nothing here is a claim about another machine.

- **Which machine counts.** `scripts/timed-check-machine.json` holds the recorded model and CPU, written from the real `sysctl` output of the maintainer's laptop. Only a machine with that model and that CPU enforces the budgets. On any other machine, and where `sysctl` is missing or has no such key (Linux), the script prints `timed check: skipped (not the recorded machine: found "X", recorded "Y")` (both bounded to 80 printable characters; `found "no sysctl answer"` where sysctl is missing) and exits 0. It never prints "within budget" or "passed" for a machine it did not verify, and it skips before it times anything.
- **A busy host (added 2026-11-13).** The script samples the 1-minute load at the start, between the two timings and at the end, and calls the host busy when a sample is above half the CPUs (the measurement lanes' rule). Load only adds time, so a time within budget on a busy host still counts, and a run that does not print the expected report always fails. Only an over-budget time measured on a busy host is not a measurement: the script prints `timed check: skipped (host busy: load L on N CPUs; an over-budget time on a busy host is not a measurement)` and exits 0, never "within budget". Found when a `npm run verify` on 2026-11-13 timed the demo at 2.25 s with a load average of 72 on this machine.
- **The timed check waits for the load to settle first (added 2026-11-13).** The verify steps before it (the test run and the build) load every CPU, and a 1-minute load average takes about a minute to fall, so before timing the script waits, in steps of 2 s and for at most 2 minutes (`SETTLE_MAX_MS` = 120,000 ms), until the 1-minute load is half the CPUs or less. Load that verify itself made fades within that time, so on an otherwise quiet machine the timing starts quiet and an over-budget time FAILs; only load that lasts (other work on the machine) can still make the run busy and lead to `skipped`. An assumed load (`--load`, a test hook) never changes, so the script does not wait for it, and the tests pass `--load 0` by default. (`scripts/timed-check.mjs`, `settle`; `test/scripts/timed-check.test.ts`)
- **The budgets are the two numbers above and no others.** A run that is slow because the machine is busy is re-run once when the load is lower; a budget is never changed to make a step pass.
- **A fast run must be a real run.** The demo run must print `demo/expected/first-run.txt` byte for byte and exit 1; the tree run must report `1000 files read` and exit 0 or 1. A crash that ends quickly therefore cannot look fast.
- **The generated tree** is written into a folder under `os.tmpdir()` outside the timed region and removed afterwards, also when a run fails. It holds 1,000 files: 600 Deployments (alternately Node and gunicorn with the uvicorn worker, each with a preStop and a grace period), 200 Services, 100 Terraform files (queue, function, event source mapping), 96 Node source files, 1 ALB Ingress and 3 ConfigMaps of 4,777,841 bytes each (100,000 keys in one map, under the 5,000,000-byte file limit), about 17.5 MB in all. It is one honest shape of "1,000 files, each under 5 MB", not the worst case: a different shape (for example one map with more, shorter keys, or deep nesting) can cost more, which is why the work is also bounded by the limits above rather than by this timer.
- **What is recorded with each result:** machine model, CPU, Node version and date are printed on the result line, and also written to `.cache/timed-check-result.json` (git-ignored).
- **The hosted workflow** (a checked file that has never run) would run on Linux, so the step would be skipped there. The budgets are therefore enforced only where the maintainer runs `npm run verify` locally.
- **The demo** is `demo/` (the first run, exit 1) and `demo-fixed/` (after the documented fix, exit 0). `demo/expected/first-run.txt` and `demo/expected/after-fix.txt` are the real output of the built command and are compared byte for byte by `test/e2e/demo.e2e.test.ts`. A test applies the documented edits to a copy of `demo/` and compares the result with `demo-fixed/`.
- **A malformed identity file is an error, not a skip.** The file must be a JSON object with a non-empty text `model` and `cpu`; anything else (`{}`, `null`, an array, a number, empty text, invalid JSON, a missing file) exits 2 with one fixed message and no crash.
- **An overridden run says so.** `--machine-file`, `--cli`, `--runs` other than 3 and `--only` are test hooks. When any is used, every result line and the last line end `(<names> overridden: not the real check)`, and the last line never says `on the recorded machine`.
- **One comparison for both budgets.** `overBudget(seconds, budget)` is `seconds >= budget` ("under": equal is over); it is unit-tested at 1.99, 2, 29.99 and 30.

## SAM and CloudFormation (B12, 2026-11-12)

Evidence: `docs/lookups-b12.txt` (dated lookups of 2026-11-12, none failed). `test/kb/cfn-evidence.test.ts` checks every CloudFormation knowledge-base entry against it word for word.

### What is read (an allow-list; nothing else counts)

- **Which file is a template.** By content, after parsing (a text test only picks candidates): a mapping that has `AWSTemplateFormatVersion`; or `Transform` together with a `Resources` key of any form, or a `Transform` string starting `AWS::`; or a non-empty `Resources` mapping whose every value is a mapping with a string `Type` of the form `A::B` (at least one starting `AWS::`). A YAML file is a candidate when a template key (`AWSTemplateFormatVersion`, `Transform`, `Resources`) is a key of the top-level mapping of a document, at the indentation that document's first line of content uses (so a template whose keys are all indented is read, while a nested `Resources:` in a Helm values file, a Serverless Framework file, a Compose file or a workflow is not a candidate); `Resources` alone counts only when the text mentions an `AWS::` type. A candidate is first parsed in the ordinary way (alias limits intact) and decided by shape; only a real template is parsed again in template mode, where an alias, a merge key and the rest are reported. A candidate that is not a template is ignored, and one that does not parse is reported with the ordinary YAML code. Measured 2026-11-12 (user CPU, `tripcurve .` on 1,000 values-like files, Node 22.23.2, Apple M5, against `main`): nested `Resources:` 0.71-0.75 s on main and now, 1.84 s with the any-indentation rule of the first B12 review fix; top-level `Resources:` with no `AWS::` 0.72-0.76 s on main, 0.71-0.73 s now, 1.71-1.76 s before. A file that is a candidate for Kubernetes too (an `apiVersion` line and a `kind` line) is parsed and decided by its documents: a Kubernetes object is a mapping with a string `apiVersion` and `kind`, so a template carried as text inside a `ConfigMap` stays Kubernetes and a template that carries a manifest as text stays a template. A `.json` file nothing else names (not `package.json`, a lock file or `*.tf.json`) is a candidate when it mentions `"AWSTemplateFormatVersion"`, or `"Resources"` with `"Type"` and `"AWS::"`, or `"Transform"` with `AWS::Serverless`.
- **Not guessed.** A file that holds both a template document and a Kubernetes object, or (for the one file named as the root) a Terraform plan and a template, is reported as not checked (reason `template-ambiguous`) and read as neither. A candidate that is not a template by shape is ignored without comment. A template of several YAML documents, and a template that uses an alias, a merge key, a collection key or a tag on a key, are reported (`cfn-unreadable`) and give no resource. A `Resources` that is present but not a mapping is `cfn-unreadable`.
- **A `.json` file that cannot be read** is reported like a `.yaml` file: permission denied, a link that leaves the root, a broken link, and a file that fails to read are listed with their reason. The one thing ignored is a `.json` file that fails to read for SIZE (over 5 MB) or ENCODING (not valid UTF-8, a NUL byte) and whose first 1 MB of raw bytes (the documented deploy limit of a template body, so any deployable template has its markers inside the window) holds none of: the ASCII markers `AWSTemplateFormatVersion`, `AWS::Serverless`, `"Type"` together with `"AWS::`, or `"Resources"` together with `"AWS::`; a NUL byte; a UTF-16 byte-order mark. NUL bytes and a UTF-16 mark mean the bytes cannot be searched as text, so such a file is always reported. With no sign that it is a template, tripcurve does not report it. With a sign it is reported with its reason (`over-size`, `unreadable` or `truncated`). That is a content test, not a name test. A marker after the first 1 MB is not seen: a template that large is not deployable (S3 limit 1 MB), so this is a documented bound, not a known miss. The 1 MB limit for a template body in S3 is looked up (`docs/lookups-b12.txt`); that UTF-8 is required is not, so no claim rests on it.
- **Only `.yaml`, `.yml` and `.json` are read** (the requirement names YAML and JSON). A template saved as `*.template`, `*.txt` or with no extension is not read and not reported: a known limit. The same applies to a `*.json` file that is not a template, which is ignored.
- **Syntax errors in a `.json` file** are worded "JSON syntax error (or a key written twice)" (reason `json-parse-error`), including `*.tf.json`.
- **Types and values.** `AWS::ElasticLoadBalancingV2::LoadBalancer` (`LoadBalancerAttributes`, the entry with `Key` `idle_timeout.timeout_seconds`; `Type`), `AWS::SQS::Queue` (`VisibilityTimeout`), `AWS::Lambda::Function` and `AWS::Serverless::Function` (`Timeout`), `AWS::Lambda::EventSourceMapping` (`MaximumBatchingWindowInSeconds`, `EventSourceArn`, `FunctionName`), and SAM `Events` of `Type` `SQS` (`Queue`, `MaximumBatchingWindowInSeconds`). They fill the same model as the Terraform readers (`form: 'cfn'`), so T4 is unchanged. A SAM event is one mapping named `<function>/<event>`, quoted like any name. A `Kinesis` or `DynamoDB` SAM event is a mapping whose source is a stream: UNRESOLVED, as in Terraform. Other event types (and `MSK`, `MQ`, `SelfManagedKafka`, `DocumentDB`) make no mapping.
- **A literal** is a number whose source text is plain decimal digits with no leading zero (so `0x10`, `0o17`, `1e2`, `060`, `60.0`, `+60`, a quoted number and a tagged value are not read as numbers), inside the documented range. The Lambda `Timeout` range is 1 to 900 s; the live Lambda page (read 2026-11-12) also gives 5,400 s for Lambda Managed Instances and for asynchronous and event source mapping invocations. A `Timeout` above 900 s is kept UNRESOLVED ("outside the documented range"), which is conservative: no PASS or FAIL rests on it. The ALB attribute `Value` is a string in CloudFormation: a number or a quoted plain integer is read. Anything else is UNRESOLVED with a fixed reason; the input text of a name, key or tag is never in the reason.
- **Tags.** A short-form tag (`!Ref`, `!GetAtt`, `!Sub`, `!If`, an unknown `!Bogus`, a verbatim tag) is rewritten in the syntax tree to its long form, a one-key mapping, before the value is made (the yaml library would otherwise drop an unknown tag and hand over the bare value). Nothing is run, no new dependency.
- **References.** `Ref` and `Fn::GetAtt` are followed one hop and only to link: the event source as `Fn::GetAtt [queue, Arn]` of an `AWS::SQS::Queue` of the same template (a `Ref` of a queue is its URL, not its ARN), the function as `Ref` or `Fn::GetAtt [function, Arn]` of a function of the same template. A parameter (even with a `Default`: parameter files are not read and a deploy can override it), `Fn::Sub`, `Fn::If`, `Fn::FindInMap`, `Fn::ImportValue`, `Fn::Select`, `Fn::Join`, a nested stack output (`AWS::CloudFormation::Stack`, `AWS::Serverless::Application`), a stream, a literal ARN, or a name that is not a resource of the template is UNRESOLVED. A cycle or self-reference cannot loop (one hop, own-property lookup) and is unresolved.

### An absent value is a claim of absence (the B1 and B5 lessons)

- **SAM `Globals`.** A function without its own `Timeout` takes `Globals.Function.Timeout` (read as a literal, with the Globals line as its source). `Globals` or `Globals.Function` that is not a plain mapping (a string, a list, empty, an intrinsic) makes the function's `Timeout` UNRESOLVED, never the default. A plain `AWS::Lambda::Function` does not take Globals.
- **`Transform`.** Exactly `AWS::Serverless-2016-10-31` as a string is read. These checks come before `Resources` is looked at, so a template with a macro and no `Resources` is listed too. Any other value (a list, `AWS::Include`, `AWS::LanguageExtensions`, a custom macro) or `Fn::Transform` anywhere makes every resource of the template UNRESOLVED, and the file is listed as not checked (`cfn-transform`). An `AWS::Serverless::` resource without the SAM transform, or a resource with no readable `Type`, gives the same (`cfn-unreadable`).
- **A `Condition` on the resource, or `Properties` that are not a plain mapping** (an intrinsic, a list, empty) make every value of the resource UNRESOLVED.
- **Defaults.** Only for a template read in full: `VisibilityTimeout` 30 s, Lambda and SAM `Timeout` 3 s, ALB `idle_timeout.timeout_seconds` 60 s (application only: an absent `Type` is the documented `application`; `Type` another literal or not a literal is UNRESOLVED). Basis `documented`, may give PASS or FAIL. Knowledge-base subjects `cfn-lb-idle-timeout`, `cfn-sqs-visibility`, `cfn-lambda-timeout` (a new data file, not the Terraform entries).
- **The batching window matches B5:** an absent `MaximumBatchingWindowInSeconds` is the ASSUMED 0 s; T4 is UNRESOLVED and the assumption (worded for the template, not Terraform) is listed.
- **A load balancer of a template is read but not linked** to an Ingress: there is no CloudFormation link form in `tripcurve.yaml`, and its `Name` is not read. `terraformIdle` works on it, so a later link form needs no new reader.

### Not read, ignored without comment

CDK code (its `.ts` or `.py` files are only what the Node and Python readers read them for), the `cdk.out` folder (never walked, like `node_modules`), `parameters.json`, `samconfig.toml`, and a nested stack's own template (only the `AWS::CloudFormation::Stack` resource is seen). Standard input is not read as a template.

### Lookup speed (a change in intake)

The path lookup of a parsed YAML document (`sourceAt` and the like) is now one walk with a key index per mapping, instead of `getIn`, which scans the keys of a mapping for every step. Without it a template with many thousands of resources made reading quadratic; a test checks linear scaling.

### Terraform claims and unreadable templates (review of B12, m5c)

`IacReadResult.incomplete` now counts Terraform inputs only: every claim it backs (a load balancer of a declared name, "exactly one `aws_lb` has this name") is about Terraform, and a template cannot hold an `aws_lb`. An unreadable template sets `incompleteTemplates` instead, and the file is listed under "Files not checked" with its own reason, so no Terraform wording is shown for it.

### Links to a `.json` file that cannot be followed (review of B12, R2)

A `.json` file is a candidate, so a link named `*.json` that dangles, loops, or leaves the checked root is listed under "Files not checked" (`unreadable`, `symlink-loop`, `outside-root`) and the run is not clean, exactly as for a `.yaml` link. tripcurve cannot sniff a link it cannot follow, and an unread input is not silently ignored once its class is relevant. To avoid it: remove the link, or run on a narrower path. (Maintainer decision to confirm before release: a link to a JSON file nothing names could instead be ignored when it dangles.)

### `incompleteTemplates` has no consumer yet (review of B12, R5)

`IacReadResult.incompleteTemplates` says a template was not read in full. Nothing uses it today, because a CloudFormation load balancer is not linked to an Ingress (the `tripcurve.yaml` schema has no form for it). Any future CloudFormation link must be wired to it, or a claim of absence over templates would ignore a template that was not read.

### A contrived non-template that is reported (review of B12, third pass)

A values file that has BOTH a top-level `Transform:` and a top-level `Resources:` key and also an alias or a merge key is reported `cfn-unreadable`: its shape is a template shape (a `Transform` with a `Resources` key), and a template that uses an alias is not read. This is kept on purpose; no ordinary values, Compose, workflow or OpenAPI file has both keys at the top. A flow-style template (`{AWSTemplateFormatVersion: ..., Resources: {...}}`, plain or quoted keys) in a `.yaml` file is read.

## The measurement lanes (B8, 2026-11-12)

`node measure/lanes.mjs <pinned|latest>` runs each knowledge-base entry's measurement script and compares the
measured value with the entry value within the entry's own tolerance. `npm run verify:measure` runs the pinned
lane. It is a separate labelled step and is not part of `npm run verify`: it starts real servers on
127.0.0.1, takes minutes, and its timings are sensitive to machine load. `npm run verify` runs only the lane
logic, against recorded lines and fakes, plus a gap test and a planted-drift test, in
`test/kb/lanes.test.ts`. The details are in `measure/README-lanes.md`.

- **Which entries have a script, which carry a reason, which are deferred.** Every entry that can run locally has a script: the Node idle close and explicit `keepAliveTimeout` and buffer entries, the gunicorn and uvicorn keepalive and graceful-timeout entries, and the lightship delay (36 entries). Nine entries carry `notMeasurableLocally` (shown `NOT RUN`): ALB idle, Kubernetes grace, the four Terraform and AWS defaults, and the three CloudFormation defaults added in B12. That reason is valid only when all of these hold (B8, enforced by the loader, by the lane's gap check and by the lane's verdict): the basis is `documented`; the subject is one of a closed list of services that cannot run on localhost (ALB/ELB, Kubernetes, AWS Lambda, SQS, the Terraform provider schema and CloudFormation defaults); and the runtime is never one the scripts can start (node, gunicorn, uvicorn, lightship). Anything else is a gap and the lane does not run. The three old-Node `headersTimeout` entries are runnable software, so they no longer carry that reason: they carry `deferredTo: {bolt: "B13", reason}` (a new optional entry field, validated by the loader, with no script and no tolerance; B8). The fact that stops them is that Node 10, 12 and 13 have no arm64 macOS build and this host has no x64 runtime (Rosetta 2 is absent: `arch -x86_64 /usr/bin/true` fails with "Bad CPU type in executable", checked 2026-11-12). Bolt B13 attempted the measurement on 2026-11-12 and recorded that it cannot run here (`measure/results/2026-11-12-b13-attempt.txt`, `measure/README-b13.md`): no release up to Node 15 has an `osx-arm64` build, and Rosetta 2 is not installed; installing it, or using an x64 host, is the maintainer's decision. The entries keep basis `from changelogs, not measured`. The lane prints them as `DEFERRED (B13)  ... not measured: <reason>`, counts them apart ("3 deferred and not measured") and never as a pass. They are not release blockers, because their basis `from changelogs, not measured` is an allowed basis; the line says they are unmeasured. `--explain` prints them as `deferred to B13: not measured (<reason>)` (B8 fix; tested in `test/report/explain.test.ts`).
- **A widening of the "not measurable locally" rule, logged for the maintainer.** The rule names the ALB idle and Kubernetes grace entries. The four Terraform and AWS default entries (Terraform ALB idle, SQS visibility, Lambda timeout, Lambda batching window; added in B5) carry the same reason, which goes beyond the letter of the rule. The widening is still "recommendation adopted, maintainer to confirm". The three CloudFormation default entries added in B12 (`cfn-lb-idle-timeout`, `cfn-sqs-visibility`, `cfn-lambda-timeout`, runtime `cloudformation`) are in the same position and are on the same closed list (merge of main into B8, 2026-11-12).
- **The resolution rule.** The comparison fails when the script's stated resolution (`sweepStepMs` + `injectedLatencyMs` + `pollMs`, whichever it prints) is coarser than the case tolerance, or when the line states none. The lightship script polls every 20 ms, so its tolerance of 10 ms was below its own resolution: it is re-derived below.
- **What a lane run does not cover.** One run per case, not three: the entries' tolerances were set from three
  runs, so a single run can in principle land outside one and fail; the lane does not retry, because a retry
  would hide a real difference. Explicit Python keepalive runs only the smallest value of the entry's span
  (`--full` adds the largest, 300 s, which takes 5 minutes a case). A K between the measured values, the
  interior of a version range (releases the entry does not cite), the precedence of settings given in several
  places, and platforms other than the one the lane runs on are not run.
- **The latest lane** looks up the newest release of each runtime (GET only), installs it into `.cache/` with
  its checksum or hash verified, runs the same cases, and fails when the newest release of a runtime is outside
  every range of that runtime. A failed lookup stops the lane with exit 4; it is not read as "nothing newer".
  The lane reports a difference and changes no knowledge-base value.
- **Per-value tolerance, and the margin.** Each case line prints its tolerance and its margin (tolerance minus the absolute deviation). A proportional tolerance (gthread explicit keepalive) is not allowed to hide a one-second error at 300 s: for a value that has observations of its own the entry carries `toleranceMsAt` (the largest deviation at that value plus the 1 ms resolution), and the lane uses it; the relative rule applies only to other values. A test checks that every planned case, `--full` included, has a tolerance below 1 s and that a run 1 s out fails.
- **Which observations a tolerance is derived from.** Only observations taken one at a time: B2 (its runs go one after another) and the B8 lane runs at `--jobs=1` or alone. Runs taken beside other timings stay in `measure/results/` as evidence and are not a basis: B2 `-b2-explicit-300` (five cases at once), B4 and B4-more (two or three lanes at once), the lane runs at `--jobs=2` and `--jobs=4`, and the first uvicorn reruns (taken while the lane default was 2). `test/kb/tolerance-evidence.test.ts` lists every result file as a basis or as evidence only, asserts the observation counts, and recomputes every derived tolerance.
- **Uvicorn worker.** Every case that runs the uvicorn worker also requires that the uvicorn release in its environment is one a uvicorn entry covers (the worker's timers are uvicorn's code), and the default case reads the worker class back from gunicorn's startup line (`py-idle-close.mjs` gained that field; the change is additive).
- **Plan coverage.** The cases planned for an entry must cover every worker class, source, value K and options-form run the entry names; a name no case covers is a gap, not a silent drop.
- **One script binds a non-local address, and lightship has no option for it.** `lightship-b4.mjs` (B4) runs lightship 9.1.0, whose own status server is started with a fixed host. `src/factories/createLightship.ts` lines 153 to 156 of the installed package (`.cache/lightship/node_modules/lightship/src/`) read `const address = await app.listen({ host: '0.0.0.0', port: modeIsLocal ? 0 : configuration.port, });`. The configuration type (`src/types.ts`) has `port` and no host, and the README documents no bind option. So the script cannot move it to 127.0.0.1 without editing lightship, which is not done. The listener is on a random free port in local mode, or on `LIGHTSHIP_PORT` (a free port the script picks) in Kubernetes mode, for the few seconds of the run; the application server the script measures listens on 127.0.0.1. This is a known departure from "localhost only", accepted because the 5 s delay is lightship's own behaviour and cannot be measured otherwise.
- **Tolerances B8 derived, with the rule and the data (second).** The rule is the largest observed deviation plus the resolution, over the basis files only: runs taken one at a time on a host that was not busy, or from before the lane printed the host load. Uvicorn `--timeout-graceful-shutdown 5` (0.54.x): 22 observations, +115.8 to +203.6 ms, plus the 10 ms polling resolution: `toleranceMs` 214 (it was 160, then 208, then 229 while one run of unknown load was a basis). Lightship 9.x delay: its script polls every 20 ms, which is the resolution, and the old tolerance of 10 ms was below it; 14 observations, +0.6 to +3.9 ms, plus 20: `toleranceMs` 24. The gthread figures are in the gthread paragraph above. Every Node entry is re-derived the same way (second): the Node tolerances are now 5 ms, except `node-idle-close-26x` and the two `node-explicit-buffer-26x` entries are 4, because their basis maximum is 3 ms. They are asserted below 100 ms, so a 1 s buffer stays decidable. All 110 lines of the official pinned run and all 65 of the official latest run were recomputed against these tolerances and every one passes (smallest margin 1 ms).
- **A run on a busy host is not a basis, and not an official run.** The lane samples the 1-minute load average at its start, before every case and at its end, prints the start and end, and calls the run busy if any sample is above half the cores. A busy run that otherwise passes prints `LANE PASS (host was busy: not an official run)` and exits **5**; a busy run that fails stays `LANE FAIL` and exits 1. Exit codes: 0 clean pass, 1 lane failed or a knowledge-base gap, 2 usage, 4 the lane could not run, 5 passed on a busy host. The basis test (`tolerance-evidence.test.ts`) requires every basis file with a paired `.txt` to show non-busy start and end lines; a file with none must be on a commented list of runs from before the load line existed. The runs made while loaded or aborted are kept as `*-loaded-*` and `*-busy` files (evidence only). `lanes-pinned-review-run1-fail` (a `--jobs=1` run whose load is unknown, taken after the load-line code existed) is evidence only. The official pinned and latest files were made before the exit-5 rule; their recorded start and end loads (2.42 and 1.21, 1.21 and 0.78, on 10 cores, threshold 5) pass it; no mid-run samples were recorded.
- **Parallel runs.** The runner starts one script at a time by default (`--jobs=1`): a timing measurement must not share the CPU with another one. A higher `--jobs` is allowed and prints `measurements ran in parallel; timing may be skewed`. Two earlier full runs were made in parallel and are kept as evidence: `measure/results/2026-11-12-lanes-pinned-jobs4.txt` (4 at once; one case read +8 ms against a 5 ms tolerance, Node 22.23.5, explicit buffer 1000 ms, K = 7 s; alone it read +1, +3 and +2 ms), `2026-11-12-lanes-pinned-jobs2.txt` (2 at once, passed) and `2026-11-12-lanes-latest-jobs2.txt` (2 at once, three failures that led to the tolerance re-derivation above and in the uvicorn graceful entry: 0.54.x, largest deviation 198 ms over 14 runs, plus the 10 ms polling, so `toleranceMs` 208).
- **Release checklist (for B15).** The release checklist must list every `DEFERRED` entry by name (today `node-headers-trap-10x`, `-12x` and `-13x`, deferred to B13) and say that each is unmeasured, so a release never reads a deferred entry as measured.

## Real-repository check (B14, 2026-11-12)

Four trimmed copies of public repositories were run and every result judged against the real files (`test/fixtures/real/README.md`, with the results table; `test/e2e/real-repos.e2e.test.ts`). No wrong verdict was found. These are the gaps that left every real run UNRESOLVED or one-sided. Each follows the approved spec, so each is documented here, not changed.

- **`envFrom` on a gunicorn container.** A `configMapRef` or `secretRef` may inject `GUNICORN_CMD_ARGS`, so T1 is UNRESOLVED even for a plain command (peermetrics `web`: `envFrom` at `k8s/base/web.yaml:37`). A `tripcurve.yaml` declaration cannot settle it; the setting must be a literal flag in the command or a linked gunicorn config.
- **An image with no command, or an image no file builds.** tripcurve links a Dockerfile to a workload only through a `tripcurve.yaml` `dockerfile:` declaration, and a Node source only through the command or a `source:` declaration. DevOpsDojo's `frontend` names an image that no file builds, so `frontend/server.js` is read only with a declaration. The server is identified only from the container's command or args (a Node, gunicorn or uvicorn program), an official `node` image tag, a linked Dockerfile's `FROM`, or a `runtime.node` declaration; a `dockerfile:` or `gunicorn_config:` declaration does not identify a Python server by itself (checked on a copy of peermetrics `api`, 2026-11-12). B17 changed the hint for such a workload (it named `runtime.node`, which misled for the Python image of peermetrics `api`): it now says what identifies each kind of server (the command or args of the container; for Node also `runtime.node`, with `source` for the entry file), as fixed text (`DECLARE_PROGRAM` in `src/resolve/idle-close.ts`). The reason line, "the server is not identified as a Node program", is unchanged: it is part of the approved report grammar.
- **The assumed ALB idle timeout.** Real manifests rarely set `idle_timeout.timeout_seconds`, so T1 is UNRESOLVED with "assumed 60 s" even when the server's idle close is known. Declaring `load_balancer.idle_timeout_s` (with `ingress:`) settles it.
- **Imported packages and "no drain".** A Node server that imports `express` is UNRESOLVED for T2 and T3 (N1 above), so a typical Express app never reaches a T2 FAIL.
- **Terraform links are folder-scoped, and integer arithmetic on literals is read (B17, 2026-11-12).** The first check (B14) found `sorah/publikes` and `DanielDaCosta/apiGateway-sqs-lambda` UNRESOLVED because the queue, the function and the mapping sit in different files of one folder, and `visibility_timeout_seconds = 60 + (30 * 6)` was an expression. The maintainer delegated the change on 2026-11-12: a reference now links within its own folder (Terraform's own module rule, quoted above under "The link between mapping, queue and function"), and integer arithmetic on literals is evaluated exactly. publikes is now a PASS (240 s covers 6 x 30 s + 60 s = 240 s) and DanielDaCosta a FAIL (the default visibility 30 s is below 6 x 30 s = 180 s, whatever the batching window is). The remaining Terraform limits stand: a variable, a local, a function, `count`, `for_each`, a `module` block, a subfolder and an override file are UNRESOLVED.
- **A `--config` file outside the checked folder** (B17) is shown exactly as it was typed, quoted as input text, in the human report, in JSON (`configErrors[].file`, `unchecked[].file`, a chain source) and in SARIF (the location): never resolved. Before B17 it was printed as an absolute real path, which shows the home directory and differs between machines. A file inside the checked folder is shown relative to it, whatever way it was typed. A typed relative path that equals the name of a file of the checked folder gets a leading `./` so that the two cannot be taken for one file. In SARIF (review of B17) such a file is located by a `file:` URI of its resolved path with no base, because it is not under the checked root and a typed relative path would resolve against the wrong folder; the human report and JSON keep the path as typed, so the resolved path (and a home directory in it) appears only in the SARIF location.
- **Kustomize `resources:`** are not followed: a `kustomization.yaml` is only a file that was read, and the manifests it lists are read when they are in the checked folder.

## The minimatch override (B16, 2026-11-12)

`package.json` carries `"overrides": { "minimatch": "11.0.8" }`. Why: `npm audit` reported GHSA-g3hv-75wg-m249 (a denial of service in `minimatch`, vulnerable range 7.0.0 to before 11.0.1) through `ts-morph` 28.0.0, the newest release, whose `@ts-morph/common` 0.29.0 asks for `minimatch` `^10.0.1`; the only other fix offered was a downgrade to `ts-morph` 17, a breaking change. With the override `npm audit` prints `found 0 vulnerabilities` and the lockfile has 123 packages.

Why it is believed safe, and what was checked on 2026-11-12:

- `@ts-morph/common` uses only `minimatch.minimatch(path, pattern)` (its `dist/ts-morph-common.js`, lines 1199 and 1287), and that call works on 11.0.8: loaded from `@ts-morph/common`'s own directory, `require('minimatch').minimatch` is a function that matched `a/b.ts` against `a/*.ts` and did not match `a/b.js`.
- `minimatch` 11.0.8 declares `engines.node` as `20 || >=22`, which includes every Node release tripcurve supports.
- `npm run verify` passed with the override, and the test suite passed on Node 22.12.0, 22.23.5, 24.22.3 and 26.13.1 (`docs/release-checklist.md`, "Compatibility across Node releases").
- The vulnerable input is a glob pattern. tripcurve does not pass patterns from the files under check to `ts-morph`; that reasoning was not tested, and `ts-morph` was not exercised on every path that reaches `minimatch`.

The override is a pin the maintainer should drop when `ts-morph` ships a release that bumps `minimatch` itself, and `npm audit` and `npm ls minimatch` should be run again on the day of the maintainer's go.

## Scaling tests on Node 24 (B16, 2026-11-12)

Two scaling tests (`test/waive/scaling.test.ts`, "an inline waiver with n blanks, n backslashes or n quotes in its reason", and `test/parse/python-pins.test.ts`, "work grows linearly with each file kind") failed on Node 24.22.3 only, with ratios of 8.05 and 9.3 to 11.9 against the limit of 8, and passed on Node 22.12.0, 22.23.5 and 26.13.1. The review of B16 found that work linear below a size and quadratic above it has a linear step below and slipped through; the simulated-clock tests for it (thresholds 1500, 2000, 3000 and 3900, two cost constants), for n to the power 1.8 (breaches) and for n log n (passes) failed before the 16 rule (8 of them) and pass after it. Quadratic work breaches at every step, and `test/core/scaling-helper.test.ts` shows both cases with a simulated clock: one cost jump inside a step reads linear, and quadratic work, with or without a jump, still breaches. The test for the jump failed (12 against 8) before the change.

A second Node 24.22.3 run failed `test/scripts/timed-check.test.ts`, "the generated tree has 1,000 files, none over 5 MB, and is removed afterwards", because it listed the `tripcurve-timed-*` folders of the shared temporary folder before and after, and another test run on the host created some in between (reproduced on 2026-11-12 with a background loop that creates and removes such folders: two of three runs failed). ## B21 (2026-11-14): fixes from the hardcore local testing

Measured on one machine (macOS arm64, Node 22.23.2, 2026-11-14). Every number below was run by hand with the built command; nothing was run on Linux.

### A Node or TypeScript source is read in linear time, and one size bound is stated

- **Cause of the hang.** Reading a source of repeated declarations (`var a = 1;` many times) was quadratic in the number of statements. The walk asked ts-morph `isExported()` for every variable statement, which asks the TypeScript binder for the symbol; the binder appends each declaration of a name to that symbol's list after scanning the list for it. A profile of a 400 KB file put 847 of 1,200 ms in that scan. The export keyword and the `export { name }` and `export default name` forms are now read from the syntax, so no symbol is ever requested (`test/parse/node-source-linear.test.ts` fails at once if one is). What is not followed is unchanged: an options object that the file exports in any of those ways is still not followed to its literal.
- **Before and after, `.ts` file of `var a = 1;` lines, the demo's three manifests beside it (run time of the whole command, peak resident size):**

  | size | before | after (this fix, below the node bound) | after (over the bound) |

  | 200 KB | 0.8 s, 217 MB | 0.6 s, 217 MB | |

  A 4.8 MB array literal took 4.7 s and 1.4 GB before (the report that found the hang measured 19 s; the time depends on the machine, the shape does not), and 1.1 s and 826 MB after, listed `source-too-large`. - **What is left is per-node cost, so the input is bounded.** After the fix the walk costs about 3 to 4 microseconds and 0.4 to 0.5 kB of memory per syntax node in the shapes measured with the whole command at 400 and 900 KB (table below): statements, calls, arrays, objects, functions, assignments, `createServer` and `listen` lines, signal handlers, repeated names and exports, each between 0.4 and 1.1 s at 900 KB. A source with more than **500,000 syntax nodes** (`MAX_SOURCE_NODES`) is not read: it is listed under "Files not checked" as `source-too-large` ("source too large to read safely"), nothing is read from it, and every claim that depended on it is UNRESOLVED (T1 says "source too large to read safely", T2 "no drain found" is UNRESOLVED, never FAIL). The bound is a count of the parsed tree, not a size in bytes and not a clock, so the output does not depend on the speed of the machine. How it was chosen: 500,000 nodes read in 1.5 to 1.9 s with a peak resident size of 342 to 405 MB for the three densest shapes measured at the bound (a 950 KB statement file, an array of 950 KB, a 950 KB file of call statements), and the ordinary code measured (a 1.5 MB file of handlers, about 470,000 nodes) in 1.5 s and 336 MB. Ordinary code has about one node per 3.4 bytes, so the bound is about 1.7 MB of ordinary code; the densest text has one node per 2 bytes, about 1 MB. A source file between those sizes and the 5 MB file limit is the case the bound exists for; a bundled server file that large is listed, not read.
- **Per-file bounds do not bound the total.** A tree of N large files costs about N times one file: 30 source files of 900 KB took 21 s in all (measured in the review of B21). No limit on the number of source files read is set.
- **The parse itself is not bounded by the count.** The node count is made after the file is parsed, and the 5 MB file limit still applies first: parsing a 4.8 MB file of the densest text takes about 0.4 to 0.7 s and leaves a peak resident size of up to 826 MB (measured on the array literal). That is the worst case of the whole command.
- **A node count above the bound for the entry file or for a file it imports is the same:** the search is not complete, so "no setting found" is never claimed (the same allow-list as for a syntax error).

### A source file that does not parse is named

A syntax error in a linked or imported source is listed under "Files not checked" as `source-parse-error` ("syntax error in a source file") with the line of the first error, and T1 says "the source could not be parsed" instead of "no server construction found". This replaces the reason code `parse-error` for source files, which was worded "YAML syntax error"; YAML, `package.json` and JSON files keep `parse-error` and `json-parse-error`. The source reader's other failure, a tree so deep that the stack overflows, stays `over-depth`. The Node reader's unchecked files now reach the report (before, they only made the search incomplete).

### A Kubernetes manifest is found by its parsed shape

- **The rule.** A `.yaml`, `.yml` or `.json` file (any case) that has the words `apiVersion` and `kind` anywhere in its text, in any quoting or style, is a candidate; it is Kubernetes when a parsed document is a mapping with an `apiVersion` key and a string `kind` (a `kind: List` with `items` included), or a sequence at the root. The reader then identifies the object or lists it as `object-not-identified`, exactly as for plain YAML, so an `apiVersion` that is not text is listed in every form, not skipped (B22: see "B22" below; it is listed for every text `kind`, also one tripcurve does not read, and in plain YAML too). So JSON, quoted keys (`"apiVersion": v1`) and a flow mapping on one line (`{apiVersion: v1, kind: Pod}`) are read, with the same findings and the same count of files read as the block-style twin (the line numbers differ). The old rule needed a plain `apiVersion:` line and a `kind:` line; a file with both stays Kubernetes on that rule, without a shape check (unchanged), and so does any file the parse leaves unreadable.
- **A file that is a list of objects at its root** (a JSON array, a flow sequence `[{apiVersion: ...}]`, a block list with `- apiVersion:` at column 0) is read element by element, like the items of a `kind: List`; an element that is not an object with a text `kind` is listed under "Files not checked" as `object-not-identified`, and a sequence of the two words with no object at all is listed the same way. The same holds when such a list is one document of a stream (B22, below). That kubectl itself accepts a root array is not claimed: tripcurve only never skips one silently.
- **A candidate that does not parse is reported.** A truncated or broken manifest in these styles is listed under "Files not checked" (`parse-error`, or `json-parse-error` for a `.json` file) and the run is not clean. A candidate that parses and holds no such mapping (a JSON data file that mentions the two words) is ignored without comment, as any file that is not ours.
- **Names that keep their class:** `package.json`, lock files, `*.tf.json` and Terraform JSON are classified by name before any of this. A file that is Kubernetes and a CloudFormation or SAM template stays `template-ambiguous`.
- **A `.json` file that is too large or not UTF-8** is listed (over-size or unreadable) when its first 1 MB of raw bytes holds the words `apiVersion` and `kind`, as it already was when it held a template marker; one without them is ignored.
- **Lookup speed.** The pre-filter is two substring searches; the candidate is parsed once with the ordinary bounded parser, and again as a Kubernetes file only when it is one. `test/parse/k8s-forms.test.ts` shows linear growth for JSON, quoted keys, one-line flow style and many small manifests.

### The package, the automation files and the lane script

- **A shrinkwrap file ships with the package and does not make the package audit clean once it is taken into a project.** The package manager reads overrides only from the root manifest, so the `minimatch` override protects the checkout and nothing else (its documentation, read 2026-11-14, is quoted in `docs/lookups-b21.txt`). The tarball now carries a shrinkwrap file, the same tree as the lock file it replaces; the manifest's `files` list names it, because the packer leaves it out otherwise. In the checkout the audit reports 0. A fresh project that takes the packed tarball gets `minimatch` 10.2.6 and the audit reports 4 moderate advisories (GHSA-g3hv-75wg-m249, with no fix offered through ts-morph 28.0.0, the newest version), because the package manager keeps a shrinkwrap entry only while it satisfies the range its dependent declares, and `@ts-morph/common` 0.29.0 declares `^10.0.1`. The commands and their output are in the B21 check-run file in `docs/`. The shrinkwrap still pins the rest of the tree, and "the audit is clean" holds for the checkout only; `test/docs/package-shrinkwrap.test.ts` pins the gap and fails when ts-morph's range reaches 11. tripcurve never calls the matching code (it reads files from an in-memory file system and never expands a glob), but that is a statement about the code, not a clean audit. Options for the owner, none adopted: bundle the dependencies (tried in a scratch copy: the audit then reports 0, the tarball grows from 0.3 MB to 3.2 MB, and the dependency listing marks `minimatch` invalid against `^10.0.1`); wait for a ts-morph version that allows 11; or replace ts-morph. Whether a library export should ship a shrinkwrap at all is also the owner's call (the documentation calls it recommended for command-line tools and discouraged for libraries).
- **No source maps in the tarball.** `tsconfig.build.json` sets `"sourceMap": false`; nothing reads a map.
- **Each automation file runs once for a same-repository pull request.** The push trigger is limited to `main`; the pull-request trigger keeps no filter.
- **`node measure/lanes.mjs <lane> --only=<id>`** on an entry with a stated reason or a deferral prints `NOT RUN (partial: --only): <id> carries a stated reason; nothing to measure` (or `... is deferred to <bolt>; nothing to measure`) and exits 2, instead of `LANE FAIL (partial: --only): 0 of 0 cases`. A full lane is unchanged.

## B22 (2026-11-14): documentation corrections and small code items

### A manifest-shaped document is never dropped without a word

- **An `apiVersion` that is not text.** A mapping with a text `kind` and an `apiVersion` key whose value is not text (a number, a boolean, `null`, a list) is listed under "Files not checked" as `object-not-identified` ("a Kubernetes object could not be identified"), in every form (block YAML, quoted keys, flow mapping, JSON, an item of a `kind: List`, a document of a stream) and for every text `kind`, including a kind tripcurve does not read (a `ConfigMap`). Before B22 the listing depended on the kind and on whether the object had a name: a nameless Deployment was listed, a `ConfigMap` was ignored, a named Deployment was read and not listed. A Deployment, Service or Ingress with such an `apiVersion` is still read, and the file is listed besides, so the run is not clean. The rule that only a `kind` that is not text makes a mapping not a manifest is unchanged: `{"apiVersion": 3, "kind": 5}` is ignored without comment. A manifest with a text `apiVersion` and a kind tripcurve does not read is ignored without comment, as before.
- **A root list inside a stream.** A document of a multi-document stream that is a list whose mappings carry an `apiVersion` or a `kind` key, none with a text `kind` (for example `[{"apiVersion": "v1", "kind": 5}]`), is listed, as the same list was when it was the whole file. A list nested inside such a list is searched too (`- - {apiVersion: apps/v1, kind: Deployment}`), alone or in a stream. A list of plain strings or of mappings with neither key is still ignored. Tests: `test/parse/k8s-b22.test.ts`.

### A `--config` file that was never opened names no line

A `--config` file that is missing, is a directory, is over the size limit or cannot be opened gave "Config error in ... at line 1", which is meaningless for a file that was never read. The human report now prints `Config error in "<file>": the config file could not be read.` with no line. The JSON `configErrors[].line` stays a number, 1, and SARIF keeps its `startLine` of 1: the JSON contract fixes `line` as an integer in every error, and a consumer reads a number there, so an absent line would be a contract change. A syntax error keeps its real line in every format. Tests: `test/cli/config-error-formats.e2e.test.ts`.

### The human summary carries the unresolved count when nothing was checked

With nothing checked and a file or waiver unresolved, JSON carried `unresolved: n` and the human summary said only "nothing checked". It now reads, for one file that could not be parsed, `Summary: nothing checked, 1 unresolved (1 file not checked); not a clean result`; with no unresolved item it is unchanged. The outcome and exit code (2) are unchanged. The three formats now carry the same counts. Tests: `test/report/summarize.test.ts`, `test/cli/config-error-formats.e2e.test.ts`.

### Workload names in SARIF are data fields

SARIF carries the workload name in `runs[0].results[].properties.tripcurve.workload.name` (a property bag; tripcurve writes no `logicalLocations`). It is the whole name, as JSON carries it, written with every character above `~` escaped as `\uXXXX`, so no control, bidirectional or invisible character reaches a file raw. It is not cut or reduced to printable ASCII like the quoted text of a message, because a property is a data field and must equal the JSON value; a viewer that renders properties as text would show the name. A name that appears in message text is quoted and bounded, like the human report. (`docs/ci-and-sarif.md`)

### Text of the documentation

- There is no `check` subcommand (two pages named one): the command has one form, `tripcurve [options] [path]`. The documents say "a run of `tripcurve [path]`", and `test/docs/docs.test.ts` fails on any published text that shows a subcommand (derived from `--help`).
- The "What ran" figures of `docs/release-checklist.md` and the CHANGELOG are re-run and dated; the CHANGELOG has one entry per bolt, B0 to B22.

## B24 (2026-11-14): a closed output pipe

- **A closed pipe ends the writing quietly.** When the reader of standard output or standard error closes early (`| head`, `| cmp - file`, a closed terminal), tripcurve stops writing, prints no trace and no message, and exits with the code the run computed (0, 1, 2 or 3), or 1 when none was known yet. What the reader received is then only a prefix of the output, and the exit code is the only report of the result; Node reports a closed pipe on POSIX as an `EPIPE` error event and ignores SIGPIPE (`docs/lookups-b24.txt`).
